# 단계별 에이전트 운영 사용자 가이드

개정: 2026-11-08 · 대응 워크플로우: 2026-11-08 개정 · 관리 구조 버전: `5`

이 가이드는 [단계별 에이전트 운영 워크플로우](../workflow/entry.md)를 실제 프로젝트에서 사용하는 방법을 설명합니다. 운영 규칙의 원본은 workflow/의 역할별 문서입니다. 배포 묶음의 폴더 구조를 유지하면 문서 간 링크로 이동할 수 있습니다.

버전 5에서는 `[계획]`, `[실행]`, `[통합]`, `[사용자검증]`을 수동 단계로 구분하고, 별도의 `[커밋]` 보조 명령으로 저장소 변경 목록을 작성할 수 있습니다. 사용자가 직접 `[총괄]`을 호출했을 때만 확정된 계획의 지정 범위에서 자동 진행합니다. 사용자검증은 확정 기준에 따른 시험 안내와 결과 기록이며, 최종 수락은 통합 담당자가 판단합니다. 운영 기록은 계속 유지하지만 `.ai-work/`는 Git 추적·스테이징·커밋에서 기본 제외합니다. 총괄의 중지·재개와 읽기 전용 현황판 기준도 포함합니다. 현황판 제작과 실행기 연결은 별도 작업입니다.

버전 4의 문서 구조는 유지합니다. 작업마다 문서 하나에 지시와 결과 보고를 함께 기록합니다. 통합 수락 후에도 같은 문서를 `work-items/90-done/`에 보관하며, 증빙은 `evidence/<상위TaskID>/`에 둡니다. 별도 `reports/`와 제출 회차별 파일은 만들지 않습니다. 기존 버전 2·3·4 프로젝트는 중간 버전을 만들지 않고 6절의 절차로 버전 5에 직접 전환할 수 있습니다. 문서 개정만으로 기존 프로젝트를 전환하거나 자동 운영을 시작하지 않습니다. 기존 대화에 개정 내용이 자동 전달됐다고 가정하지 말고, 해당 대화에서 새 워크플로우를 다시 읽도록 요청하세요.

아래 요청문은 복사해서 실제 대화에 보낼 예시입니다. 문서 속 예시를 읽는 것만으로 작업이 시작되지는 않습니다. `[프로젝트 절대경로]`, 프로젝트 ID, 작업 ID와 버전은 실제 값으로 바꾸세요. 아래의 `.ai-work/serial-link/`는 예시 프로젝트 루트 아래의 관리 폴더이며, `work-items/`와 `evidence/`는 이 관리 폴더를 기준으로 한 경로입니다.

공통 설치·갱신은 [설치 안내](installation.md)를 따릅니다. 실행 중인 작업과 하위 에이전트는 시작할 때 고정한 커밋의 스냅샷을 함께 사용합니다.

## 1. 가장 먼저 할 일

1. PC에 공통 문서 묶음을 설치하고 도구의 전역 진입 지침을 연결합니다. 에이전트에게 고정 스냅샷의 `workflow/entry.md` 절대 경로를 전달할 수도 있습니다. entry.md만 따로 복사하지 말고 전체 묶음에 접근할 수 있게 합니다.
2. 작업할 프로젝트 루트와 목표를 지정합니다. 여러 저장소가 있으면 이번 작업의 경계를 명시합니다.
3. 기본 수동 모드에서는 한 번에 계획, 실행, 통합, 사용자검증 중 한 단계를 요청합니다. `[커밋]`은 제작 단계와 별개의 보조 명령입니다.
4. 수동 모드에서는 단계가 끝난 뒤 다음 단계를 별도로 요청합니다. 계획이 확정된 뒤 자동 진행을 원하면 10절의 `[총괄]`을 호출합니다.

첫 요청은 다음처럼 보낼 수 있습니다.

```text
[계획]
첨부한 [고정한 워크플로우 entry.md 절대경로]를 읽고 적용해 줘.

프로젝트 루트: [프로젝트 절대경로]
목표: 장치와의 통신에서 타임아웃을 감지하고 복구할 수 있게 만들기
필수 조건: 기존 공개 API 유지, 오류 원인 기록, 정해진 응답 시간 준수
제외 범위: UI 변경, 새 하드웨어 도입
사용 가능한 환경: 기존 컴파일러와 단위 테스트 환경
사용자가 해야 하는 검증: 실제 보드에서 통신 단절 및 복구 시험

기존 관리 기록을 먼저 확인하고 실행 가능한 작업지시서를 작성해 줘.
구현은 시작하지 말아 줘.
```

파일을 저장하거나 첨부하는 것과 특정 도구에 스킬로 설치하는 것은 별개입니다. 이 가이드는 문서를 읽게 하는 방식으로 사용할 수 있으며, 특정 앱에 대한 설치를 전제로 하지 않습니다. 기존 대화에는 개정본을 다시 읽으라는 지시를 직접 전달하세요.

## 2. 어느 단계를 선택할까

| 지금 필요한 것 | 요청할 단계 | 그 단계에서 받는 것 |
|---|---|---|
| 목표를 요구사항과 실행 가능한 작업으로 나누기 | `[계획]` | 요구사항, 공통 기준, 작업지시서, 의존 관계와 검증 목표 |
| 지정한 기능 구현·조사·문서 작성·수정 | `[실행]` | 실제 결과물과 작업 문서 안의 수행·검증 결과 |
| 결과물 결합, 요구사항 충족 확인, 수락 판단 | `[통합]` | 수락 결과 또는 수정 지시서, 전체 검증 현황 |
| 사용자가 수행할 시험 안내·결과 기록 | `[사용자검증]` | 전체 미해결 항목, 한 번에 하나씩의 시험 절차, 결과 반영과 다음 항목 안내 |
| 저장소 변경 조사와 커밋 목록 초안 | `[커밋]` | 현재 diff를 근거로 한 그룹·메시지·파일별 스테이징 명령 초안; 지정 목록 파일만 쓰며 Git 메타데이터·index·staging·소스는 변경하지 않음 |
| 확정된 계획의 지정 범위를 자동 진행 | `[총괄]` | 계획의 병렬 가능 판단에 따른 실행·통합·REV 처리와 범위 완료 또는 중단 인계 |
| 지금 진행 중인 작업과 대기 사유 확인 | 상태 조회 | 현재 상태와 기록 시점을 구분한 설명 |

태그가 없어도 목적이 명확하면 에이전트가 단계를 추론하지만, 경계를 분명히 하려면 태그를 쓰는 편이 좋습니다. 수동 요청에 여러 단계가 섞이면 한 단계를 선택하도록 요청합니다. `[사용자검증]`은 통합 수락을 대신하지 않으며, 다른 수동 단계와 동시에 시작하지 않습니다. `[커밋]`도 명시적으로 요청해야 하며 Git add·commit을 실행하지 않는 별도의 보조 작업입니다. `[총괄]` 호출만으로 커밋리스트 작성이나 실제 커밋 권한이 생기지 않습니다. 자동 운영은 추론하지 않으며 사용자가 직접 `[총괄]`을 호출해야 합니다. `[총괄]`은 확정된 계획 안에서 실행·통합·필요한 수정을 조율하는 운영 명령이며, 초기 계획을 대신하지 않습니다.

이미 목표·범위·입력·결과물·완료 조건이 충분하면 계획 없이 실행부터 요청할 수 있습니다. 결과물이 이미 있다면 기존 목표와 수락 기준을 제공하고 통합부터 요청할 수도 있습니다.

## 3. 기본 수동 사용 흐름

```text
계획 요청
  → 작업지시서 확인
  → 실행 요청
  → 결과물·자체 검증 보고 확인
  → 통합 요청
  → 수락 또는 수정 지시서

사용자 환경 시험이 남으면
  → 사용자검증 항목 전체 확인·순서 지정
  → 한 항목씩 시험 안내·사용자 결과 회신
  → 원본 문서에 기록·다음 항목 안내
  → 필수 항목을 마치면 통합 수락 요청

수정이 필요하면
  → 수정 실행 요청
  → 재통합 요청
```

### 계획 결과에서 확인할 것

계획 담당자는 기존 자료로 해소되지 않는 사용자 의도·기대 동작·범위·제약·수락 기준을 한 번에 1~3개씩 질문합니다. 확정된 요구사항 안의 구현 세부는 AI가 결정합니다. 답변이 필요한 부분을 무응답만으로 확정하지 않으며, 특정 판단을 맡기려면 그 범위를 알려 주세요. 확정된 결정은 계획 문서에 반영합니다.

목표와 제외 범위가 맞는지, 각 작업에 시작 조건과 완료 조건이 있는지 확인합니다. 계획 담당자는 최초 계획에서 병렬 가능 여부(`가능`·`조건부 가능`·`불가`), 함께 수행할 작업 ID, 판단 근거·조건, 공유 파일·문서·빌드 출력·장비 등의 소유권과 통합 순서를 작업지시서에 남깁니다. 미확정 항목은 병렬 가능으로 취급하지 않습니다. 사용할 수 없는 환경의 검증이 사용자 테스트로 구분돼 있는지도 봅니다. 표준 방식에서는 다음 파일을 받게 됩니다.

- `.ai-work/<project-id>/plan.md`: 요구사항과 공통 기준.
- `.ai-work/<project-id>/work-items/`: 상태별 작업 문서. 계획 단계에는 지시 내용을 작성하며, 수행·검증 결과는 실행 후 같은 파일에 추가합니다.
- `.ai-work/<project-id>/index.md`: 마지막 계획 시점의 전체 기준과 다음 조치.

계획 문서가 완성돼도 기능 구현이 끝난 것은 아닙니다. 지시서는 보통 계획됨 또는 준비됨 상태입니다.

### 지정 작업 실행하기

```text
[실행] T-03
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/

T-03의 현재 지시서 위치와 입력 버전을 확인하고 실행해 줘.
지정 범위의 결과물을 만들고, 같은 작업 문서 뒤에 수행·검증 결과를 작성해 줘.
필요한 증빙은 evidence/T-03/에 저장하고 연결해 줘.
제출 시각과 검증한 산출물 버전을 남기고 결과에 맞는 상태로 이동해 줘.
```

에이전트가 지시서와 필요한 자료에 접근할 수 있다면 이전 대화를 모두 붙여 넣을 필요가 없습니다. 파일 접근이 불가능한 대화에는 지시서와 명시된 필수 참조 자료를 함께 전달합니다.

실행이 끝나면 실제 결과물, 검증한 버전, 작업 문서의 수행·검증 결과와 증빙 링크, 미검증 항목과 다음 행동을 확인합니다. 정상 제출의 작업 상태는 검토 대기입니다. 실행 담당자의 자체 검증은 통합 수락과 구분됩니다.

### 결과 통합·수락 요청하기

```text
[통합] T-03, T-04
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/

각 작업 문서의 최신 제출 시각·산출물 버전과 실제 결과물을 확인해 줘.
공통 기준과 완료 조건에 따라 연결 부분을 검증하고 수락 여부를 판단해 줘.
검토·수락 판단은 해당 작업 문서의 이력에 기록해 줘.
실질적인 수정이 필요하면 REV 작업 문서를 남겨 줘.
```

통합은 지정 범위의 결과물과 유효한 검증 근거를 직접 확인합니다. 수동 통합에서 수정이 필요하면 지시서를 작성하고 종료합니다. 통합 요청만으로 수정 구현까지 자동 진행하지 않습니다. 활성화된 총괄 범위 안에서는 총괄이 수정 실행과 재검토를 배정합니다.

## 4. 작업 ID와 폴더로 상태 읽기

### 상위 Task와 하위 작업의 이름

상위 Task는 `T-<번호>`, 하위 작업은 `T-<상위번호>-<TYPE>-<하위번호>`를 사용합니다. 작업 ID와 파일명은 일치하며, 제목은 문서 안에 씁니다.

| 작업 ID | 파일명 | 의미 |
|---|---|---|
| `T-01` | `T-01.md` | 상위 Task |
| `T-01-REV-01` | `T-01-REV-01.md` | T-01의 첫 수정 작업 |
| `T-01-EXT-01` | `T-01-EXT-01.md` | T-01의 첫 외부 환경 작업 |
| `T-01-VAL-01` | `T-01-VAL-01.md` | T-01의 첫 검증 작업 |

유형은 대문자 `REV`, `EXT`, `VAL`로 통일합니다. 검증이 목적이면 외부 환경에서 시험해도 `VAL`을 사용합니다. 별도 환경 준비·접근 확보 등은 `EXT`로 구분합니다. 새로운 유형이 필요하면 계획·통합 담당자가 코드와 적용 기준을 먼저 정의합니다.

번호는 상위 Task와 유형별로 각각 매깁니다. 따라서 `T-01-REV-01`과 `T-01-VAL-01`이 함께 있어도 됩니다. 기본은 두 자리 숫자이며 기존 프로젝트의 자릿수는 유지합니다. 사용한 ID는 재사용하지 않고, 재제출만으로 새 ID를 만들지 않습니다.

하위 작업을 다시 수정할 때도 ID를 중첩하지 않습니다. 예를 들어 `T-01-REV-01`이 이미 배정된 상태에서 `T-01-VAL-01`을 수정해야 한다면 다음 ID인 `T-01-REV-02`를 만들고, 문서의 수정 대상 ID에 `T-01-VAL-01`을 적습니다. 여러 Task에 걸친 작업은 책임지는 상위 Task 하나를 정하고 나머지는 관련 작업 ID로 연결합니다.

`.ai-work/` 아래 새 파일·폴더 이름은 ASCII 영문자·숫자·하이픈·밑줄·마침표만 사용합니다. 작업 문서 파일명에 제목·날짜·상태를 덧붙이지 않습니다. 문서 내부 제목과 내용은 한국어로 작성합니다. `index.md`, `plan.md` 같은 공통 관리 문서는 고정 영문 이름을 유지합니다.

### 상태 폴더

상위 Task와 하위 작업 모두 `.ai-work/<project-id>/work-items/` 아래에 있습니다. 상태가 바뀌면 지시·결과 보고·검토 이력이 담긴 파일 하나가 이동하며 ID와 파일명은 유지됩니다. 증빙과 실제 결과물은 고정 위치에 남습니다.

| 폴더 | 뜻 | 사용자에게 주로 필요한 다음 행동 |
|---|---|---|
| `00-planned` | 시작 조건 확인 전 | 필요한 입력·결정 확인 |
| `10-ready` | 시작 조건 확보 | 실행할 작업 선택 |
| `20-in-progress` | 실행 수행 단계 | 진행·차단 기록 확인 |
| `30-review-pending` | 제출 완료 또는 외부 검증·입력 대기 | 통합 요청 또는 요청받은 검증 결과 제공 |
| `40-in-review` | 통합 담당자가 수락 검토 중 | 검토 결과 확인 |
| `50-changes-requested` | 수정 필요 확인 | 연결된 수정 작업의 실행 요청 |
| `60-blocked` | 외부 조건으로 진행 불가 | 해제 조건·담당 확인 |
| `90-done` | 통합 수락 완료 | 수락 대상 버전 확인 |
| `99-cancelled` | 승인된 취소·대체 | 취소 사유·대체 작업 확인 |

위 표의 다음 행동은 수동 모드 기준입니다. 검증 항목별 상태(`통과`, `실패`, `미수행`, `사용자 검증 대기`, `해당 없음`)는 작업 상태와 별도로 기록합니다. 총괄 운영 중에는 승인된 범위에서 실행·통합·REV 배정을 총괄이 수행하며, 사용자 결정이나 외부 검증이 필요한 항목은 인계합니다.

사용하지 않는 상태 폴더가 없어도 정상입니다. 폴더는 절차상 상태를 나타냅니다. `20-in-progress`에 있다는 것만으로 에이전트가 지금 실행 중이라고 단정하지 말고, 현재 담당자·갱신 시각·다음 행동을 함께 확인하세요.

직접 폴더만 옮기면 근거와 상태가 어긋날 수 있습니다. 상태 정정이 필요하면 이유와 대상 ID를 알려 담당 에이전트가 관련 기록까지 맞추도록 요청하는 것이 좋습니다.

### 수정 작업 실행과 재통합

다음은 `work-items/` 안의 상태 예시입니다.

```text
20-in-progress/
  T-03-REV-01.md

30-review-pending/
  T-04.md

50-changes-requested/
  T-03.md
```

- `T-03`은 원래 통신 구현 작업이며 수정이 필요합니다.
- `T-03-REV-01`은 T-03의 첫 수정 작업이며 현재 실행 단계입니다.
- `T-04`는 제출됐고 통합 검토를 기다립니다.

수동 모드에서 수정할 때는 `REV` 작업을 지정합니다.

```text
[실행] T-03-REV-01
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/

수정 지시의 허용 범위에서 수정하고 필요한 자체 검증을 수행해 줘.
T-03-REV-01.md 뒤에 수행·검증 결과와 제출 이력을 작성해 줘.
수정 대상과 상위 Task T-03을 명시하고 증빙은 evidence/T-03/에 저장해 줘.
```

수동 모드에서는 수정 제출 뒤에 별도 메시지로 요청합니다.

```text
[통합] T-03-REV-01 및 원래 작업 T-03
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/

수정 결과와 영향받는 연결 부분을 확인하고 각각 수락 여부를 판단해 줘.
각 작업 문서에 대상 버전과 판정을 남기고 수락한 문서만 90-done/으로 옮겨 줘.
```

하위 작업이 완료돼도 상위 Task가 자동 완료되지는 않습니다. 원래 Task의 다른 수정이나 필수 검증이 남아 있을 수 있습니다. 수락된 문서는 계속 `work-items/90-done/`에 두며 별도 `99-archive/`로 옮기지 않습니다.

## 5. 작업 문서와 증빙 확인하기

### 작업 문서 하나에서 확인하는 내용

문서 상단에는 작업 ID·요구사항 ID·지시서 개정·현재 담당자·갱신 시각·다음 조치·최신 제출 시각과 산출물 버전이 있습니다. 하위 작업에는 상위 Task, 수정 작업에는 수정 대상도 표시합니다. 아직 제출하지 않은 작업은 미제출로 구분합니다.

본문은 다음 순서로 읽습니다.

| 절 | 확인할 내용 |
|---|---|
| 작업 지시 | 목적·범위·입력·제약·완료 조건·검증 목표 |
| 수행 결과 | 최신 변경·결정·사용한 입력·산출물 버전·진행 상황·다음 조치 |
| 검증 결과·미해결 문제 | 항목별 검증 상태·근거·증빙 링크·위험·사용자 테스트 요청 |
| 제출·검토·상태 이력 | 제출·반려·재제출·수락의 시각·담당자·대상 버전·판정 이유와 상태 이동 |

재제출할 때는 같은 문서의 바뀐 결과 항목·메타정보만 부분 수정하고 이력에 변경 이유와 대상 버전을 짧게 추가합니다. 변하지 않은 지시와 표를 다시 생성하거나 전체 보고를 매번 뒤에 쌓지 않습니다. 최신 문서와 참조만으로 재개할 수 있게 유지하며 제출 회차별 파일은 만들지 않습니다. 이전 판정 이력은 유지하고 중요한 근거는 증빙이나 복구 가능한 버전으로 연결합니다. 지시서 개정은 요구사항·범위·수락 기준이 실질적으로 바뀔 때 올립니다.

최신 제출 이후 미제출 변경이 있는지도 확인하세요. 같은 산출물 버전을 여러 번 제출했다면 제출 시각으로 구분합니다. 과거 수락이 새로운 산출물 버전까지 자동으로 보증하지는 않습니다.

### 증빙은 상위 Task별로 모으기

아래는 필요한 문서와 증빙이 생긴 뒤의 구조 예시입니다. 실제 결과물은 프로젝트에 맞는 소스·산출물 위치에 저장합니다.

```text
.ai-work/serial-link/
├── index.md
├── plan.md
├── work-items/
│   ├── 30-review-pending/
│   │   └── T-01-VAL-01.md
│   ├── 50-changes-requested/
│   │   └── T-01.md
│   └── 90-done/
│       └── T-01-REV-01.md
├── evidence/
│   └── T-01/
│       ├── T-01-external-evidence-01.md
│       ├── T-01-REV-01-test-log-01.txt
│       └── T-01-VAL-01-test-log-01.txt
└── integration.md
```

`T-01-REV-01`과 `T-01-VAL-01`의 증빙도 모두 `evidence/T-01/`에 둡니다. 하위 작업 ID별 증빙 폴더를 따로 만들지 않습니다. 작업 문서에서 해당 증빙을 연결하며 작업 상태가 바뀌어도 증빙은 이동하지 않습니다.

증빙 파일명은 `<작업ID>-<evidence-type>-<번호>.<확장자>`입니다. 종류는 `external-evidence`, `test-log`처럼 소문자 영문과 하이픈으로 표시하고 같은 종류에 같은 이름을 씁니다. 번호는 작업 ID와 증빙 종류별로 매깁니다. 판정에 사용한 증빙은 덮어쓰지 않고 새 증빙을 추가합니다. 증빙 파일에는 독립된 작업 상태가 없으며 수행 결과 요약은 작업 문서에 작성합니다.

### 현재 상태 조회하기

| 기록 | 의미 |
|---|---|
| 작업 문서가 놓인 현재 폴더 | 현재 운영 상태 |
| 작업 문서의 수행·검증 결과 | 최신 결과 요약과 미제출 변경 여부 |
| 작업 문서의 제출·검토 이력 | 특정 시점·버전에 대한 제출과 판정 |
| `index.md` | 마지막 계획·통합·총괄 판단 시점의 기준 상태와 운영 요약 |
| `dashboard/status.json` 및 HTML | 구현된 경우에만 제공하는 조회용 스냅샷 |

`index.md`는 실시간 프로세스 현황판이 아니므로 현재 폴더·실행 상태와 다를 수 있습니다. 날짜와 대상 버전을 확인해야 합니다. 자동 모드에서 `index.md`는 총괄이 갱신하고, 통합 담당자는 작업 문서의 판정과 `integration.md`를 담당합니다. 수동 `[사용자검증]` 담당자는 작업 문서와 `index.md`의 현재 갱신 담당자에게 각각 소유권을 인계받은 뒤 검증 현황과 다음 조치만 한정해 `index.md`를 갱신할 수 있습니다. 총괄은 통합 판정을 대신하지 않습니다.

```text
프로젝트 루트: [프로젝트 절대경로]
.ai-work/serial-link/의 현황을 조회해 줘.
현재 작업 문서 위치와 수행·검증 결과, 제출·검토 이력을 확인하고,
index.md의 마지막 갱신 시점과 구분해서 설명해 줘.
진행 중, 검토 대기, 검토 중, 수정 필요, 막힘을 나눠 알려 줘.
각 대기 항목의 이유, 다음 행동과 담당자도 포함해 줘.
기록 변경이나 구조 전환, 새 작업은 시작하지 말아 줘.
```

상태 조회만으로 기록 변경이나 구조 전환이 시작되지는 않습니다.

### Git 제외와 결과물에 내부 정보 노출

`.ai-work/`의 작업 문서와 증빙은 계속 생성·갱신하지만 Git 추적·스테이징·커밋에는 기본 포함하지 않습니다. 적절한 기존 Git 제외 설정을 사용합니다. 이미 추적 중인 관리 파일은 해당 프로젝트와 요청 범위의 로컬 자료·복구 가능성을 확인하고 보존한 뒤, 기본 제외 규칙에 따라 Git 추적에서만 해제합니다. 과거 Git history를 자동 재작성하지 않습니다. 다른 clone·worktree에서 관리 자료에 접근할 수 있는지 확인하고, Git 밖 복구 사본이 필요하면 따로 보존합니다. 내부 기록에서 제품 커밋·버전으로 결과물을 추적하세요.

커밋 메시지, 제품 코드·프로젝트 결과물의 주석, PR 설명, 최종 사용자용 문서에는 내부 작업 ID·작업 문서명·`.ai-work/` 경로를 기본 노출하지 않습니다. Git 제외 설정에 동작상 필요한 경우 `.ai-work/` 경로를 넣는 것은 허용됩니다. 프로젝트 산출물은 의미 중심의 기술 표현을 사용합니다. 사용자가 지정한 대상과 행위에 한해서만 예외를 적용하며, Git 포함 요청은 다른 위치에 ID나 관리 경로를 노출할 허가가 아닙니다. 이 가이드는 운영 설명이므로 예시에서 내부 ID와 경로를 사용할 수 있습니다.

## 6. 기존 프로젝트를 구조 버전 5로 전환하기

버전 2·3·4에서 버전 5로 직접 전환할 수 있습니다. 중간 버전의 가이드나 구조를 만들 필요는 없습니다. 버전 4의 ID·문서·상태 폴더·증빙 구조는 유지하고 필요한 운영 메타정보만 보완합니다. 자동 운영 활성화나 현황판 설치는 전환에 포함하지 않습니다. 기존 대화에 개정 워크플로우를 전달하고 다음처럼 요청합니다. 이는 계획 단계의 관리 작업이며 구현을 시작하는 요청이 아닙니다.

```text
[계획]
2026-11-08 개정, 관리 구조 버전 5의 [고정한 워크플로우 entry.md 절대경로]를 읽고 적용해 줘.

프로젝트 루트: [프로젝트 절대경로]
기존 관리 기록: .ai-work/serial-link/
이번 범위: 기존 관리 구조를 버전 5로 전환하고 실행 준비 상태 정리

실제 구조와 layout_version을 확인해 줘.
진행 중 담당자와 경로 인계를 확인하고, 미커밋 문서까지 복구 수단을 확보해 줘.
버전 4라면 기존 ID·폴더를 유지하고 필요한 운영 메타정보를 보완해 줘.
더 오래된 구조라면 상위 Task와 하위 유형을 확인한 뒤 ID·파일명·현재 참조를 맞춰 줘.
기존 reports/가 있으면 최신 유효 결과를 해당 작업 문서에 합치고 과거 제출·판정 근거는 복구 가능한 버전 또는 evidence/<상위TaskID>/의 legacy-report 증빙으로 보존해 줘. 제출 회차별 새 보고서를 만들지 말아 줘.
증빙은 evidence/<상위TaskID>/에 정리해 줘.
전환 근거·이전/새 ID·이전/이후 경로·미확정 항목을 migration.md에 남겨 줘.
검증이 끝난 뒤에만 layout_version: 5를 기록해 줘.
전환 후 상태와 다음 작업을 인계하고 구현이나 새로운 수락 판단은 시작하지 말아 줘.
```

이미 통합할 결과물이 있다면 통합 요청에 개정본 재확인과 구조 확인을 포함해도 됩니다. 계획·통합 담당자는 본 작업 전에 전환을 처리합니다. 실행 담당자에게 프로젝트 전체 개편을 맡기지는 않습니다. 총괄 시작 때 전환이 필요하면 통합 담당자에게 관리 작업으로 맡기며, index.md 갱신 권한도 전환 동안 한 명에게 인계합니다.

전환 완료 보고에서는 다음을 확인합니다.

- 기존 작업 문서가 누락되거나 중복되지 않았는지.
- 이전 ID와 새 ID의 대응이 남아 있고 현재 명령·본문·의존 관계·파일명·링크가 일치하는지.
- 최신 수행·검증 결과가 작업 문서에 합쳐졌고 과거 제출·판정 근거를 복구할 수 있는지.
- 증빙이 상위 Task별 고정 폴더에 모였고 작업 문서에서 열 수 있는지.
- 현재 상태와 수락 버전이 근거 없이 바뀌지 않았는지.
- 진행 중 담당자에게 바뀐 경로가 인계됐고 모든 전환이 끝난 뒤에만 `layout_version: 5`가 기록됐는지.

예를 들어 이전 `R-T-03-01`은 `T-03-REV-01`로 바뀝니다. 이전 `T-EXT-*`, `T-VAL-*`나 유형 없는 하위 ID는 번호만으로 상위 Task를 추정하지 않습니다. 문서의 목적·의존 관계를 확인해 대응을 정하고, 새 ID가 충돌하면 덮어쓰거나 임의로 재번호하지 않습니다.

기존 보고서 원문은 확인된 복구 버전으로 보존하거나, 복구 버전이 없으면 `evidence/<상위TaskID>/<새ID>-legacy-report-<번호>.md`로 보존합니다. 원문과 근거의 보존을 확인한 뒤 기존 보고서를 정리합니다. 이 파일은 과거 기록 보존용이며 이후 제출마다 만드는 보고서가 아닙니다.

상태·상위 Task·유형이 불명확하거나 인계가 안 된 문서는 원위치에 남을 수 있습니다. 이때 전환은 미완료이며 `migration.md`에 필요한 확인과 재개 조건을 남깁니다. 중단 후에는 새 관리 폴더를 만들지 말고 같은 프로젝트에서 대응표와 실제 파일을 대조해 남은 전환을 이어갑니다. 이미 현재 구조라면 반복 개편하지 않습니다.

워크플로우나 사용자 가이드만 수정해 달라는 요청은 기존 프로젝트 전환 요청이 아닙니다. 문서 저장만으로 다른 대화에 개정 규칙이 전달됐다고 가정하지 말고, 기존 담당자에게 개정본을 다시 읽으라는 지시를 직접 전달하세요.

## 7. 사용자 검증을 직접 수행할 때

`[사용자검증]`은 확정된 기준에 따라 사용자가 직접 시험하도록 안내하고, 제출된 결과를 원본 작업 문서에 기록하는 단계입니다. 제품을 수정하거나 새 환경을 자동 설치하지 않으며, 통합 수락을 대신하지 않습니다. 필수 사용자 검증이 끝나도 최종 수락은 `[통합]`에서만 합니다.

### 요청 범위와 시험 안내

단일 프로젝트가 분명하고 범위를 생략하면 그 프로젝트의 미해결 사용자 검증 항목 전체를 대상으로 합니다. 대상 프로젝트가 여러 개이고 범위를 지정하지 않았다면 프로젝트를 확인하도록 요청하세요. 특정 작업만 진행하려면 작업 ID를 지정합니다.

전체 범위 요청 예시:

```text
[사용자검증] 프로젝트 전체
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/

현재 작업 문서와 확정된 검증 기준을 확인해 줘.
미해결 사용자 검증 항목 전체를 작업 ID, 항목 ID, 내용, 대상 버전,
준비 조건, 의존 관계, 현재 상태와 함께 먼저 목록으로 보여 줘.
의존 관계와 준비 조건에 따라 순서를 정하고, 한 번에 하나씩 안내해 줘.
내 OS·shell과 프로젝트 환경에서 실제 실행 가능한 복사 명령,
실행 위치, 기대 결과, 실패 기준, 제출할 로그를 확인해 줘.
GUI·물리 조작이 필요한 항목은 수동 절차도 포함해 줘.
명령이나 환경이 확인되지 않으면 만들어내지 말고 필요한 정보만 물어봐 줘.
새 환경을 설치하거나 제품을 수정하지 말고 결과를 기존 문서에 기록해 줘.
```

특정 작업 요청 예시:

```text
[사용자검증] T-03
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/

T-03의 미해결 사용자 검증 항목을 확인해 줘.
먼저 해당 항목과 대상 버전·준비 조건·의존 관계·현재 상태를 알려 주고,
내 환경에서 실제 실행할 수 있는 명령 또는 수동 절차를 한 항목씩 안내해 줘.
기대 결과, 실패 기준, 회신할 로그·관찰 결과를 포함해 줘.
```

먼저 범위 안의 미해결 항목을 모두 목록으로 받고 시험 순서를 확인합니다. 그다음 에이전트가 한 항목씩 다음 내용을 안내해야 합니다.

- 실행 위치와 운영체제 shell, 준비 조건
- 실제 프로젝트와 사용자 환경에서 복사해 실행할 수 있는 명령
- 기대 결과와 실패 기준
- 회신할 로그 또는 관찰 결과
- GUI·보드·장비처럼 명령으로 할 수 없는 조작이 있으면 정확한 수동 절차

프로젝트 환경이 제공되지 않은 상태에서 제품 명령을 추측해 실행하지 마세요. 환경 정보가 필요하면 AI에게 OS·shell·도구 버전 등 명령을 정하는 데 필요한 정보만 물어보라고 요청합니다. 명령의 실제 지원 여부를 확인할 수 없다면 AI가 그 한계를 밝혀야 합니다.

검증 기준에 항목 ID가 없으면 기존 작업 문서 안에서 고유하고 재개 시 유지되는 ID를 정해 사용합니다. 새 `VAL` 문서나 별도 추적 원장은 만들지 않습니다. 각 검증 결과는 해당 원본 작업 문서에 기록하고 증빙은 상위 Task의 `evidence/<상위TaskID>/`에 둡니다. 예를 들어 T-03의 시험 로그는 `evidence/T-03/`에 연결합니다. 수동 사용자검증 담당자는 현재 문서의 단독 갱신 소유권을 인계받아 단계 동안 유지하며, 종료·인계 시 다음 담당자에게 돌려줍니다. `index.md`는 검증 현황과 다음 조치만 갱신할 수 있고, 자동 모드에서는 총괄이 소유합니다.

### 결과 회신과 다음 항목

첫 안내 뒤에는 결과를 기다리며 AI를 반복 호출할 필요가 없습니다. 사용자가 결과를 회신하면 같은 `[사용자검증]` 단계의 계속으로 처리됩니다. 다음 양식처럼 결과를 보내세요. 검증 응답마다 `[사용자검증]` 태그를 다시 쓸 필요가 없습니다.

```text
검증 항목: [안내받은 작업 ID와 항목 ID]
대상 버전: [커밋, 빌드 번호, 파일 해시 등]
시험 환경: [장비·OS·설정·연결 조건]
수행한 절차: [실제 수행 내용]
관측 결과: [기대 결과와 실제 결과]
로그·증빙: [첨부 또는 접근 가능한 위치]
```

에이전트는 회신의 대상 버전·시험 조건·근거를 확인하고, 사용자가 수행한 결과임을 명시해 원본 작업 문서와 고정 증빙 위치에 기록합니다. 근거가 없거나 대상 버전·조건이 다르면 통과 처리하지 않고 필요한 자료만 확인합니다. 이전 제출과 통합 판정은 보존합니다. 산출물 버전이 달라졌다면 통합 담당자가 영향받는 검증만 다시 판단하며, 영향 없는 항목을 반복하지 않습니다.

각 항목의 결과를 문서에 기록한 뒤 통과·실패·대기 상태, 남은 항목, 차단 사유와 다음 행동을 알려 주고 다음 독립 항목으로 진행합니다. 실패한 항목에 의존하는 시험은 보류하고, 독립된 시험은 계속할 수 있습니다. 근거 없이 같은 시험을 반복하지 않습니다. 항목이 하나도 없으면 없음으로 보고해야 하며 통과했다고 가정하지 않습니다.

검증 상태는 `통과`, `실패`, `미수행`, `사용자 검증 대기`, `해당 없음`으로 구분합니다. `해당 없음`은 적용되지 않는 이유를 남기며 필수 검증을 생략하는 용도로 쓰지 않습니다. 제작 자체가 외부 조건 때문에 불가능하면 작업을 막힘으로 인계합니다. 원인이 밝혀지지 않은 문제는 확인된 사실·남은 가설·다음 측정 항목을 구분해 전달합니다. 환경 준비나 별도 시험이 필요하면 사용자가 허용 범위·장비·권한·비용을 정해 별도의 `[실행]`을 요청할 수 있습니다. `[사용자검증]` 요청을 추가 환경 준비나 지정 범위 밖 시험의 승인으로 확대하지 않습니다.

사용자 검증 항목의 통과는 작업 수락이 아닙니다. 필요한 모든 항목을 통과한 뒤에는 `[통합]`을 별도로 요청하세요. 이미 시험을 마친 결과를 바로 수락 검토받고 싶으면 검증 결과를 함께 첨부해 `[통합]`을 직접 요청할 수 있습니다.

```text
[통합] T-03
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/

아래 사용자 시험 결과의 출처·대상 버전·조건·증빙을 확인해 줘.
해당 작업의 실제 산출물 버전과 나머지 수락 조건도 함께 검토하고,
유효한 결과는 사용자 수행으로 원본 작업 문서에 연결해 줘.
필수 항목이 모두 충족되는지 확인해 수락 여부를 판단해 줘.

[위 결과 회신 양식으로 시험 결과 기입]
```

### 중단과 재개

사용자 결과를 기다리는 것은 단계의 중단이 아닙니다. 제출할 자료와 대기 상태를 안내한 뒤 대화를 넘기며 반복 조회하지 않고, 사용자가 결과를 회신하면 같은 단계에서 기록·현황 갱신 후 계속합니다. 사용자가 명시적으로 중단·보류를 요청했다면 자동으로 이어가지 않으며, 재개할 때 `[사용자검증]`을 다시 요청합니다. 중단 시 처리한 항목, 마지막 확인 버전·조건, 남은 자료와 다음 행동을 기록하도록 요청하세요.

```text
[사용자검증] T-03 이어서
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/

최신 작업 문서와 대상 버전을 확인해 미완료 항목부터 계속해 줘.
이미 유효하게 통과한 항목은 반복하지 말고,
남은 시험은 기존 기준과 환경에 맞춰 안내해 줘.
```

유효한 결과물이 제출된 작업은 기본적으로 `30-review-pending`에 있으며, 사용자 검증만 남은 항목은 `사용자 검증 대기`입니다. 필수 검증이 남아 있으면 완료나 수락으로 표시할 수 없습니다. 확인된 실패에서 수정이 필요하면 원본 작업 문서에 근거를 기록하고 다음 담당자에게 인계합니다. 새 REV의 생성·지시는 계획·통합 담당자가 맡고, 이미 완료된 작업의 수락 판정을 바꾸는 권한은 통합 담당자에게 있습니다.

총괄 작업이 진행 중이면 총괄이 사용자 검증 대기를 인계받고 승인 범위의 다른 독립 작업을 계속할 수 있습니다. 사용자가 결과를 제출하면 총괄은 최신 버전과 시작 조건을 확인해 통합 담당자의 검토를 배정할 수 있습니다. 총괄이 끝난 뒤에는 결과 제출만으로 자동 재개하지 않습니다. 다시 총괄을 이어가려면 `[총괄] 재개`와 기존 실행·대상 범위를 명시합니다. 총괄 운영 중 별도의 수동 `[사용자검증]` 요청이 같은 문서에 영향을 주면 먼저 문서 갱신 소유권을 조정합니다.

## 8. 여러 대화와 모델 사용하기

환경별 기본 프로필은 다음과 같습니다. 각 계열의 최신 버전을 사용하며 표는 사용자가 지정한 2026-11-07 기준값입니다. 배정 시작 시 환경의 모델 목록과 공식 안내로 최신 버전·실제 선택명·사용 가능 여부를 확인합니다. 추론 강도를 선택할 수 있으면 `high`를 요청하고, 설정이 없는 모델은 미지원과 실제 기본 설정을 기록합니다. 수동 모드는 사용자 선택 또는 지원되는 위임으로, 총괄 모드는 배정 설정으로 적용합니다. 세부 기준은 [워크플로우 모델·재시도 규칙](../workflow/models.md)을 따릅니다.

| 역할 | Codex | Cursor |
|---|---|---|
| 계획·3단계 | GPT-6 Astra (`gpt-6-astra`) | Claude Opus 5.5 |
| 총괄·2단계 | GPT-6.1 Sol (`gpt-6.1-sol`) | Claude Sonnet 5.5 |
| 실행·REV 수행·1단계 | GPT-6 Luna (`gpt-6-luna`) | Composer 2.5 |
| 통합·수락·2단계 | GPT-6.1 Sol (`gpt-6.1-sol`) | Claude Sonnet 5.5 |
| 사용자검증·1단계 | GPT-6 Luna (`gpt-6-luna`) | Composer 2.5 |
| 커밋목록·1단계 | GPT-6 Luna (`gpt-6-luna`) | Composer 2.5 |

최신 버전 정책은 Luna·Sol·Astra·Composer·Sonnet·Opus의 지정 계열 안에서 적용합니다. 사용자가 특정 버전을 고정하면 그 지정을 우선하고, 실행 중인 담당자를 새 버전 발표만으로 교체하지 않습니다. 최신 여부를 확인할 수 없으면 기준값과 확인 한계를 밝힙니다. Cursor의 실제 선택명과 추론 강도 지원 여부도 해당 환경에서 확인합니다. 총괄과 통합은 같은 모델을 쓰더라도 별도 담당자로 두며 수락은 통합 담당자가 판단합니다. 초기 계획은 사용자가 해당 환경의 3단계 모델에서 직접 요청합니다.

Codex의 Sol 사용량 제한이 확인되면 **최신 Sol → GPT-6 Sol → GPT-5.6 Sol** 순서로 대체합니다. 위 기준일에는 **6.1 → 6 → 5.6**이며 총괄·통합과 실행의 2단계 상향에 적용합니다. 사용자검증·커밋목록의 최초 배정은 1단계입니다. 별도 승인 없이 실제 선택 가능한 후보를 순서대로 확인하되 제공되지 않는 버전은 사유를 남겨 건너뜁니다. 모든 후보가 제한되거나 계정 전체·사용자 지정 한도에 도달하면 중단·인계합니다. 작업 실패나 일반 도구 오류에 이 대체 순서를 적용하지 않습니다.

Sol 대체는 같은 단계의 버전 변경이므로 수정 재시도 누계나 상향 기회를 초기화하지 않습니다. 기존 담당자의 명령·변경·소유권을 확인한 뒤 인계하고, 대체 사유와 실제 모델을 기록합니다. 대화 모델 전환을 지원하지 않는 환경에서는 사용자가 전환해야 할 수 있으며, 문서 설정만으로 전환됐다고 보고하지 않습니다.

최초 시도는 역할별 지정 모델로 시작합니다. 실행·REV·사용자검증·커밋목록은 1단계, 통합·총괄은 2단계, 계획은 3단계입니다. 계획·통합·총괄이 어렵다고 판단하거나 작업지시서에서 높은 성능을 권고해도 최초 실행을 상위 모델로 올릴 수 없습니다. 짧은 작업의 직접 수행에도 같은 기준을 적용합니다. 사용자에게 별도 모델 지정이 있으면 그 지정을 우선하며, 지정 모델을 사용할 수 없으면 임의 상향하지 않고 제한과 인계 방법을 알립니다.

새 담당자에게는 역할·작업 ID, 프로젝트와 현재 작업 문서의 절대 경로, 고정 워크플로우 경로·커밋, 지시서 개정·제출/산출물 버전, 이번 변경점·다음 행동을 전달합니다. 상세 지시·허용 범위·결정·검증·위험은 원본의 해당 절과 증빙으로 연결합니다. 제출·검토·수정 반환 때 문서 갱신 담당자도 인계합니다. 아래 예시의 경로·버전은 실제 값으로 바꾸며 별도 인계 파일을 만들 필요는 없습니다.

```text
[실행] T-04
워크플로우: [고정 entry.md 절대경로], [워크플로우 커밋]
프로젝트: [프로젝트 루트 절대경로]
작업 문서: [T-04.md의 현재 절대경로], 지시서 [개정]
대상: [입력/산출물 버전 및 제출 시각 또는 미제출]
이번 변경: [새로 확정된 조건 또는 변경 없음]
다음 행동: 현재 담당·시작 조건 확인 후 작업 지시를 수행하고 같은 문서에 제출.
필수 참조·검증 근거·미해결 문제: 작업 문서의 해당 절과 링크 참조.
```

태그로 현재 대화의 모델이 자동 변경되지는 않습니다. 원하는 모델과 추론 강도는 환경에서 선택하거나 지원되는 위임 요청에 명시합니다. 결과 보고의 요청 설정과 실제 확인된 설정을 구분해서 읽으세요. 확인할 수 없으면 `확인 불가`로 기록합니다. 총괄 대화는 해당 환경의 2단계·high를 선택하며, 고정 설정이나 하위 에이전트 제어가 지원되지 않으면 자동 배정 전에 대안을 확인합니다.

실행·통합의 동일 문제는 **지정 모델로 최초 시도 + 수정 재시도 1회**, 즉 총 2회 실패가 확인된 뒤 **바로 위 단계 모델로 1회** 시도합니다. 성공하면 상향하지 않습니다. 상향 시도도 실패하면 추가 수정을 멈추고 시도 내역·실패 근거·남은 가설·영향·재개 조건을 보고합니다. 수동 모드는 사용자에게, 자동 모드는 총괄에게 보고하고 총괄이 사용자에게 알립니다. 상위 단계가 없거나 사용할 수 없어도 보고·인계하며, 1단계에서 2단계로 상향한 뒤 3단계까지 연속 상향하지 않습니다.

상향에는 지정 단계에서 실제 실패한 2회의 근거가 필요합니다. 예상 난도나 모델 추천, 같은 실패 로그의 중복은 횟수에 포함하지 않습니다. REV·담당자·모델 대체·재개로 누계를 초기화하지 않으며, 기존에 2회 이상 실패한 문제는 남아 있는 상향 기회만 사용합니다. 환경·권한 부족은 상향 대상이 아니고, 통합 담당이 결함을 발견한 것은 통합 모델의 실패가 아닙니다. 모델 상향도 수동 모드의 다음 단계 실행 허가를 대신하지 않습니다.

기록량과 인계 비용을 줄이는 방법은 아래 13절을 참고하세요. 세부 결과는 작업 문서 원본에서 확인합니다.

Rust 작업은 사용자 요구가 없으면 제품 소스 안에 새 테스트 전용 코드를 남기지 않습니다. 같은 Cargo 패키지의 `tests/`에 통합 테스트를 두는 것은 허용하지만 디렉토리·별도 패키지를 반드시 만드는 규칙은 아닙니다. `tests/`는 자동 커밋 제외 대상도 아닙니다. 테스트를 제외하려면 관련 설정·의존성 변경까지 함께 확인해야 합니다. 내부 검증용 임시 코드는 제출 전에 정리하고 필수 검증 근거를 남기며, 기존 테스트는 보존합니다.

## 9. 작은 작업, 취소와 자주 생기는 혼동

### 작은 작업은 간소 실행

```text
[실행]
첨부한 소개문을 500자 이내로 다듬어 줘.
독자는 처음 방문하는 고객이고, 사실과 수치는 유지해 줘.
결과는 Markdown 파일로 저장해 줘.
간소 방식으로 처리하고 변경 내용과 확인 결과를 짧게 보고해 줘.
```

다른 담당자에게 넘기거나 나중에 재개할 필요가 없으면 관리 폴더 전체를 만들 필요가 없습니다. 이미 표준 방식인 프로젝트의 등록 작업은 기존 기록 체계를 유지합니다.

### 필요 없어진 작업 취소

```text
[계획]
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/

T-06의 기능은 이번 범위에서 제외하기로 결정했어.
진행 중 담당자가 있으면 인계를 확인한 뒤 취소 사유를 기록해 줘.
관련 요구사항과 후속 의존 작업의 영향을 정리해 줘.
```

취소된 작업을 완료 폴더로 옮기지 않습니다. 대체 작업이 있다면 ID를 연결하고, 필수 요구사항이 그대로 남아 있지는 않은지도 확인합니다.

| 혼동하기 쉬운 점 | 올바른 해석 |
|---|---|
| 준비됨이므로 자동 시작한다 | 수동 실행 요청 또는 활성 총괄의 범위 내 배정이 필요합니다. |
| 자체 테스트가 통과했으므로 완료다 | 실행 제출과 통합 수락을 구분합니다. |
| 사용자 검증 항목이 통과했으므로 작업이 완료다 | 모든 필수 항목을 기록한 뒤에도 최종 수락은 통합 담당자만 판단합니다. |
| `.ai-work/`를 Git에서 제외했으므로 관리 기록을 중단한다 | 관리 기록은 계속 갱신하고 Git 추적·커밋만 기본 제외합니다. |
| `[커밋]`을 요청하면 실제로 커밋한다 | diff 조사와 커밋리스트 초안만 만들며 add·commit은 실행하지 않습니다. |
| 총괄이 실행 중이므로 커밋리스트도 자동 생성된다 | 커밋리스트는 사용자가 별도로 `[커밋]`을 요청해야 합니다. |
| 수정 지시서가 생겼으므로 바로 수정한다 | 수동에서는 별도 요청, 총괄에서는 범위·조건 확인 후 배정합니다. |
| REV 등 하위 작업이 완료면 상위 Task도 완료다 | 상위 Task의 조건과 영향받은 부분도 확인합니다. |
| 검토 대기는 에이전트가 멈춘 오류다 | 통합 요청 또는 외부 검증·입력을 기다릴 수 있습니다. |
| 오래된 index.md가 현재 상태다 | 현재 작업 문서의 위치·최신 결과·이력을 대조합니다. |
| 90-done 폴더에 넣으면 수락된다 | 통합 담당자의 수락과 버전별 근거가 먼저 필요합니다. |
| 완료 보고는 reports에 따로 저장한다 | 같은 작업 문서 뒤에 결과를 적고 수락 후 90-done으로 이동합니다. |
| 재제출마다 새 파일이나 ID가 필요하다 | 같은 문서의 최신 결과를 갱신하고 짧은 이력을 남깁니다. |
| 하위 작업의 증빙도 별도 폴더가 필요하다 | 모두 상위 Task의 `evidence/T-01/` 같은 폴더에 모읍니다. |
| 전체 요청을 한 번에 보내면 자동 운영이다 | 확정된 계획에 대해 명시적으로 `[총괄]`을 호출해야 합니다. |
| 정지 버튼을 누르면 모든 작업이 즉시 끝난다 | 하위 에이전트·명령의 실제 중단을 따로 확인해야 합니다. |
| 현황판이 새로고침되면 실행 상태도 최신이다 | 실행 정보의 마지막 관측 시각을 확인해야 합니다. |

## 10. 확정된 계획을 [총괄]로 진행하기

총괄은 이 워크플로우의 요청 규약입니다. 태그 자체가 앱에 새로운 실행기나 버튼을 설치하지 않습니다. 지원되는 하위 에이전트 배정·상태 확인·중단 기능이 있는 환경에서 사용합니다.

사용자가 계획을 확인한 뒤 해당 환경의 총괄용 2단계·high 대화에서 다음처럼 요청합니다.

```text
[총괄]
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/
대상: T-01, T-02, T-03
확정 계획: plan.md [확인한 개정 또는 버전]

확정된 계획에 따라 실행·통합과 필요한 REV 수정을 자동 진행해 줘.
역할별 지정 단계의 최신 모델과 Sol 사용량 제한 시 대체 순서를 적용해 줘.
최초 실행은 1단계로 시작하고, 동일 문제에서 지정 모델로 총 2회 실패한
근거가 있을 때만 바로 위 단계로 1회 시도한 뒤 실패하면 보고해 줘.
계획 담당자가 작업지시서에 기록한 병렬 가능 판단을 읽고,
선행 조건·입력 버전·공유 자원·담당 소유권을 확인해 줘.
독립 작업은 환경의 동시 실행 한도 안에서 별도 하위 에이전트로 병렬 수행해 줘.
실행·통합 담당자가 병렬 수행 불가를 보고하면 관련 작업을 보류하고 조정해 줘.
지정 범위가 완료되거나 중단 조건에 도달하면 결과를 인계해 줘.
```

실행 흐름은 다음과 같습니다.

```text
사용자가 [계획] 요청·결과 확인
  → 사용자가 [총괄] 호출
  → 총괄: 범위·모델·계획의 병렬 판단·현재 조건·중단 기능 확인
  → 독립 작업별 1단계 실행 담당: 병렬 실행·자체 검증·제출
  → 제출된 작업별 2단계 통합 담당: 독립성·소유권 확인 후 검토·수락
      수정 필요 → 실행 담당: REV 수행 → 통합 담당: 재검토
      수락 → 총괄: 다음 실행 가능한 작업 배정
  → 단일 2단계 통합 담당: 지정 범위 전체의 최종 연결·누락 검증
  → 총괄: 완료 또는 미완료 사유 인계
```

총괄 호출만으로 커밋리스트 작성이나 실제 스테이징·커밋이 허가되지는 않습니다. 커밋리스트가 필요하면 사용자가 `[커밋]`을 별도로 요청합니다.

총괄은 번호 순서만으로 작업을 고르지 않습니다. 작업 지시의 선행 ID·필요한 수락·입력 버전과 실제 제출·판정 근거를 확인합니다. 범위 밖 선행 작업, 순환 의존, 중요한 계획 변경은 임의 처리하지 않습니다. REV는 수정 대상의 최종 완료를 기다리는 작업이 아니며, VAL도 검증 가능한 산출물을 기준으로 시작 조건을 정합니다.

총괄은 계획에서 병렬 가능으로 판단한 작업의 현재 조건을 다시 확인한 뒤 각각 별도 하위 에이전트를 동시에 호출합니다. 이 범위의 병렬 배정에는 별도 승인이 필요하지 않습니다. 조건부 가능은 조건 충족 후 배정하고, 불가·미확정·판단 누락 항목은 순차 수행 조건을 확인하거나 계획 담당자에게 판단 보완을 요청합니다. 사용자 지정 한도와 환경 슬롯 한도를 지키며 슬롯이 부족하면 기다리거나 순차 진행합니다.

실행·통합 중 공유 파일·시험 장비 충돌이나 숨은 의존성 등으로 병렬 수행이 불가능해지면, 담당자는 영향받는 쓰기·시험을 보류하고 작업 ID·충돌 자원·근거·보존된 변경을 총괄에게 보고합니다. 총괄이 순차 전환·대기·허용 범위의 자원 분리·재배정을 지시하면 그 지시와 재개 조건에 따라 처리합니다. 총괄의 지시 없이 충돌 작업을 다시 시작하지 않습니다. 중요한 계획 변경은 사용자에게 확인합니다.

독립 작업의 통합 검토도 병렬화할 수 있지만 같은 결과물의 수정과 검토를 겹치지 않습니다. 공유 `integration.md` 갱신과 범위 전체의 최종 결합·판정은 한 통합 담당자가 직렬로 수행합니다. 병렬 조건·조정 사유는 기존 작업 문서와 운영 요약에만 기록합니다.

지정 범위의 필수 하위 작업과 필요한 REV만 처리합니다. 규정된 최신 버전 선택·Sol 대체·모델 상향은 사전 승인 범위에서 처리하지만, 새 요구사항, 승인 한도 밖 비용·새 권한·환경 준비는 자동 승인되지 않습니다. 총괄이 전체 프로젝트를 맡지 않았다면 지정 작업의 완료를 프로젝트 전체 완료로 보고하지 않습니다.

재시도·모델 상향 한도는 8절과 [워크플로우 모델·재시도 규칙](../workflow/models.md)을 따릅니다. REV ID 변경이나 재개로 횟수가 초기화되지 않습니다. 한 작업의 외부 대기·시도 한도 도달 시 독립 작업은 계속할 수 있지만, 사용자 전체 중지와 전체 실행 한도 도달 시에는 새 배정을 모두 멈춥니다. 더 진행할 작업이 없으면 외부 결과를 무한히 기다리지 않고 인계합니다.

총괄 도중 상태 질문은 할 수 있습니다. 같은 작업을 다른 대화에서 직접 수정하려면 자동 배정 보류와 담당 인계를 먼저 요청하세요. 총괄 종료 후의 일반 `[실행]`·`[통합]`·`[사용자검증]` 요청은 다시 수동으로 동작합니다. 종료된 총괄은 사용자 결과가 도착해도 자동 재개되지 않습니다.

## 11. 총괄과 하위 에이전트 중지·재개하기

### 전체 중지 요청

총괄이 응답 가능한 상태라면 다음 메시지를 보냅니다.

```text
[총괄] 중지
현재 총괄의 새 배정과 재시도를 중지해 줘.
이 총괄이 시작한 하위·자손 에이전트와 실행 명령도 중단해 줘.
중단 요청과 실제 중단 확인을 구분하고,
남은 실행·미제출 변경·재개 조건만 정리한 뒤 종료해 줘.
```

총괄은 새 배정을 막고 자신이 시작한 하위 실행과 명령에 중단을 요청합니다. 무관한 대화는 중단하지 않습니다. 실제 중단을 확인한 뒤 최소한의 기록을 남기며, 확인 불가능한 대상이 있으면 식별자와 필요한 사용자 조치를 알립니다. 중지 때문에 작업을 완료·실패·취소로 바꾸지는 않습니다.

### 앱의 정지 버튼을 눌렀을 때

정지 버튼으로 상위 응답을 먼저 끊으면 정리 절차가 실행되지 못할 수 있습니다. 하위 에이전트와 장시간 명령까지 즉시 중단됐다고 보장할 수 없으며, 이미 저장된 변경이나 수행된 외부 작업이 자동 복구되는 것도 아닙니다. 버튼 사용 후에는 다음처럼 잔여 실행을 확인합니다.

```text
[총괄] 중단 확인
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/
작업을 재개하지 말고, 이 총괄이 시작한 잔여 하위 에이전트와 명령을
확인·중단하고 상태와 미확인 대상을 정리해 줘.
```

중단 확인은 제작이나 새 배정을 재개하는 요청이 아닙니다. 확인되지 않은 실행이 남아 있으면 전체 중지 완료로 보고하지 않습니다. 현황판의 오래된 기록만으로 중단 여부를 판단하지 마세요.

### 기존 결과를 유지하며 재개

```text
[총괄] 재개
프로젝트 루트: [프로젝트 절대경로]
관리 기록: .ai-work/serial-link/
기존 실행: [index.md의 실행 식별자]
대상: T-01, T-02, T-03
해소한 중단 사유와 추가 입력: [변경 사항 또는 해당 없음]

잔여 실행·담당 인계·미제출 변경·결과물 버전을 확인해 줘.
기존 범위·모델·한도·수정 횟수를 유지하고 남은 작업부터 진행해 줘.
```

재개 시 유효한 수락과 검증을 유지하고 변경 영향을 받은 부분만 다시 확인합니다. 잔여 실행이나 문서 소유권 충돌이 있으면 먼저 해소합니다. 이미 한도에 도달했다면 단순 재개 요청만으로 한도를 늘리지 않으므로 필요한 변경을 명시하세요.

## 12. 사람이 보는 현황판

첫 버전은 **로컬 HTML 읽기 전용 현황판**을 권장합니다. 브라우저로 상태를 보고 필터링하거나 작업 문서를 열 수 있게 하고, 실행 제어는 총괄 대화에서 요청합니다. 이번 워크플로우 문서만 적용했다고 화면이 생성되지는 않으며, 제작·실행기 연결은 별도로 요청해야 합니다.

구현할 경우 관리 폴더 안에 다음 파일을 둡니다.

```text
.ai-work/<project-id>/dashboard/
├── index.html
└── status.json
```

| 화면 영역 | 확인하는 내용 |
|---|---|
| 전체 진행 | 지정 범위, 상위 Task 수락·진행·대기·막힘 수 |
| 총괄 | 운영 상태, 현재 배정, 다음 행동, 중지 사유 |
| 에이전트 | 역할, 요청·확인된 모델, 담당 작업, 실행·대기·중단 여부 |
| 작업 목록 | 작업 ID, 상태, 선행 조건, 대기 이유, 문서 링크 |
| 사용자 검증 | 검증 항목별 통과·실패·대기·미수행 상태와 대상 버전 |
| 최근 이력 | 제출, 반려, REV 시작, 수락, 중지 |
| 사용량 | 관측 가능한 역할별 토큰, 집계 시각·대상, 누락 여부 |
| 정보 신선도 | 문서·실행 정보의 관측 시각, 수집기 갱신 시각, 연결 상태 |

상위 Task와 REV·EXT·VAL 수를 따로 보여 줍니다. REV가 끝나도 상위 Task 수락이 남아 있으면 완료율에 섞지 않습니다. 사용자 검증 항목의 상태도 작업 상태와 별도로 집계합니다. 항목 통과를 상위 Task의 수락·완료로 계산하지 않습니다. 작업의 상태 폴더와 실제 에이전트 실행 여부도 분리합니다. 예를 들어 작업은 진행 중 폴더에 남아 있어도 에이전트는 중단됐을 수 있습니다.

화면은 원본 작업 문서와 관측 가능한 실행 정보로 만든 스냅샷을 표시합니다. `status.json`을 편집해서 수락이나 작업 상태를 바꾸지 않습니다. 가벼운 수집 프로그램과 화면이 갱신을 처리하도록 설계하면 5초마다 새로고침하더라도 그 갱신 자체에 AI 토큰을 쓰지 않습니다. 실제 실행 상태·사용량을 얻을 수 없는 환경에서는 확인 불가로 표시합니다.

화면을 새로고침한 시각과 실제 실행 정보를 관측한 시각은 다릅니다. 총괄·수집기가 멈추면 마지막 확인 시각과 정보 지연을 보여 줘야 합니다. 정적 HTML만 제공하는 경우 자동 실시간 조회가 아닌 수동 스냅샷임을 표시합니다. 자동 갱신에 로컬 제공 기능이 필요하면 별도 제작 범위에서 환경을 확인합니다.

전체 중지·재개 버튼은 실제 취소 전달과 중단 확인을 연결하고 검증한 뒤 추가합니다. 첫 버전에는 조회·필터·문서 열기만 둡니다.

## 13. 기록·인계 비용과 토큰·시간 한도

기본은 **사람이 읽는 작업 문서 하나 + 경로·버전·변경점 중심의 인계 + 변경 부분만 갱신**입니다. 작업지시서의 관련 항목은 짧게 묶고 공통 규칙은 참조합니다. 결과는 원본 한 곳에 쓰고 `index.md`에는 운영 요약, `integration.md`에는 연결 검증과 전체 판단만 남깁니다. 대화에는 결과·제한·다음 행동과 원본 링크를 전달합니다.

환경이 지원하면 하위 에이전트에 부모 대화 전체를 상속하지 않고 위 인계 정보만 전달합니다. 대화에만 있던 사용자 결정·제약은 먼저 작업 문서에 보존합니다. 새 담당자는 필수 규칙·작업 지시·증빙을 직접 읽어야 하며, 같은 담당자는 컨텍스트에 남아 있는 변경 없는 자료를 반복해서 읽지 않습니다. 원문 접근이 안 되거나 컨텍스트를 잃었다면 필요한 자료를 다시 확보합니다. 원본을 읽는 입력과 인계 메시지를 쓰는 출력도 토큰을 사용합니다.

한국어 Markdown을 유지하며 별도 AI용 압축본·요약 원장·인코딩본을 관리하지 않습니다. 도구의 컨텍스트 압축을 문서 지침만으로 구현했다고 보거나 다른 모델·도구로 자동 전달된다고 가정하지 않습니다. 범위·수락 기준·사용자 결정·담당·버전·미제출 변경·실패 누계·검증 근거·미해결 문제는 줄이는 과정에서도 보존합니다. 상태 이동·목록 집계는 검증된 기존 도구가 있으면 활용할 수 있지만 수락 판단을 대신하지 않으며, 새 자동화 도구 구축은 별도 작업입니다.

총괄이 작업 중으로 보이는 시간 전체에 비례해 토큰이 계속 발생하는 것은 아닙니다. 대기 도구로 하위 결과를 기다리는 동안에는 새로운 모델 추론 호출이 없지만, 실행·통합·결과 판단·추가 요약에는 토큰을 사용합니다. 짧은 간격으로 AI에게 계속 진행 상황을 묻는 방식은 피하고 완료 이벤트나 대기 기능을 사용합니다.

전체 사용량에는 총괄뿐 아니라 실행·통합과 REV의 입력·출력이 포함됩니다. 추론 토큰이 출력 집계에 포함된 환경에서는 별도 합산하지 않으며, 상위 집계에 포함된 하위 사용량도 다시 더하지 않습니다. 캐시 입력 할인과 총 토큰 수는 구분합니다. 관측되지 않은 사용량은 0으로 취급하지 않습니다.

작업 크기와 수정 횟수를 측정하기 전에는 신뢰할 수 있는 총량을 정하기 어렵습니다. 첫 작업의 역할별 사용량을 확인한 뒤 후속 범위와 한도를 조정하는 방법을 권장합니다. 저렴한 실행 모델로 나눠도 인계·재검토가 늘면 총 토큰 절감은 보장되지 않습니다.

필요하면 총괄 요청에 다음 항목을 실제 값으로 추가합니다.

```text
시간 한도: [최대 경과 시간]
토큰 한도: [모든 역할 합계 한도 또는 관측 가능한 집계 범위]
비용 한도: [금액·통화, 비용을 확인할 수 있는 경우]
한도 적용: [도구로 강제되는 상한이 필요한지, 관측 시 중단으로 충분한지]
```

지정하지 않은 수치는 미지정으로 남습니다. 자연어 한도만으로 진행 중 호출을 정확한 시점에 끊는다고 보장할 수 없습니다. 엄격한 상한이 필수인데 환경에서 집행할 수 없다면 총괄은 시작 전에 제한을 알리고 배정하지 않습니다. 전체 한도에 도달하면 새 배정을 중단하고 실행 중 대상의 중단·인계를 처리합니다. 재개한다고 기존 사용량이나 수정 횟수가 초기화되지는 않습니다.

## 14. 인계받을 때 확인할 다섯 가지

1. 어떤 모드·단계와 작업 ID를 처리했는가.
2. 실제 결과물·현재 작업 문서·증빙을 어디서 열며 어떤 제출 시각과 버전을 확인해야 하는가.
3. 어떤 버전을 어떤 방법으로 검증했는가.
4. 남은 문제·미검증 항목과 그 영향은 무엇인가.
5. 다음 행동은 누가, 어떤 입력을 받은 뒤 수행하는가.

프로젝트 전체 완료 여부는 통합 판정과 `summary.md`의 대상 버전으로 확인합니다. 실행 종료 메시지나 개별 `90-done` 항목만으로 전체 완료를 판단하지 마세요.

커밋리스트에서 인계받을 때는 프로젝트 루트·HEAD·조사 시각·확인 범위와 메시지 관례 근거를 확인하고, 실제 staging 전에 현재 diff와 목록을 다시 대조하세요. 사용자검증에서 인계받을 때는 항목 ID·현재 상태, 사용자 결과의 출처, 대상 버전·시험 조건·증빙, 남은 항목과 차단 의존성을 확인하세요. 총괄에서 인계받을 때는 실행 식별자, 실제 중단 여부와 미확인 실행, 누적 사용량의 관측 범위, 남은 수정 횟수·한도와 재개 조건도 확인하세요. 현황판을 구현하지 않았다면 해당 화면이나 제어 기능이 제공된 것으로 간주하지 않습니다.


## 15. [커밋] 변경 조사와 커밋리스트 만들기

`[커밋]`은 현재 변경을 조사해 추천 메시지와 파일별 스테이징 명령을 텍스트로 작성하는 보조 명령입니다. 실제 `git add`·`git commit`은 실행하지 않습니다. 운영 기준은 [워크플로우 커밋목록 규칙](../workflow/commit-list.md)이며 총괄 호출에 자동 포함되지 않습니다.

### 요청 예시

```text
[커밋]
프로젝트 루트: [프로젝트 절대경로]
커밋리스트 경로: [원하는 경로 또는 생략]
범위: 프로젝트 루트 아래 현재 변경 전체
실행 shell: [Bash / PowerShell / CMD 등 사용하는 shell]

staged·unstaged diff와 무시되지 않은 신규 파일 내용을 확인해 줘.
작업 또는 의미 있는 변경을 파일 단위로 묶고,
각 추천 커밋 메시지와 파일별 스테이징 명령을 작성해 줘.
프로젝트 루트 기준 상대 경로로 git add -- 명령을 한 줄에 하나씩 적고,
내 shell에서 그대로 복사해 실행할 수 있게 경로를 인용해 줘.
별도 파일 목록이나 줄 연결 문법은 사용하지 말아 줘.
같은 파일이 여러 변경에 걸치면 관련 묶음을 합쳐 줘.
라인·패치 단위 분할이나 별도 분할 관리 기록은 만들지 말아 줘.
메시지는 해당 디렉터리의 명시 규칙을 우선하고,
없으면 HEAD 포함 최근 최대 30개 커밋의 제목·본문 관례를 따라 줘.
.ai-work/와 목록 파일 자체는 제외하고, 목록 외 파일이나 Git 상태는 변경하지 말아 줘.
```

출력 경로를 생략하면 프로젝트 루트의 `commit-list.txt`를 사용합니다. 이전 생성 목록은 요청 범위에서 갱신할 수 있지만 같은 이름의 무관한 파일은 보존합니다. 프로젝트 루트가 Git 루트의 하위 폴더여도 경로 기준은 지정한 프로젝트 루트이며, 범위 밖 파일이나 여러 저장소를 한 목록에 섞지 않습니다.

### 결과 확인하기

목록 앞에는 프로젝트 루트·HEAD·조사 시각·범위·실행 shell과 커밋 메시지 관례의 근거가 표시됩니다. 이력이 30개 미만이면 있는 만큼 사용하고, 이력이 없거나 형식이 불명확하면 제안 형식과 이유를 밝힙니다. 내부 작업 ID·관리 경로·확인되지 않은 이슈 번호나 검증 결과를 메시지에 넣지 않습니다.

각 그룹은 다음 형식입니다. 아래 명령은 Bash 기준이며 실제 출력은 사용자의 shell에 맞춥니다. 전체 예시는 [커밋리스트 예시](../examples/commit-list-example.txt)에서 볼 수 있습니다. 그룹 번호는 커밋 메시지에 포함하지 않습니다.

```text
커밋 1

커밋 메시지:
[프로젝트 관례에 맞는 제목과 필요한 본문]

스테이징 명령 — 프로젝트 루트에서 실행:
git add -- "src/example.rs"
git add -- "tests/example.rs"
```

- 한 파일은 하나의 커밋에만 포함합니다. 같은 파일을 공유하는 변경은 관련 묶음을 합칩니다. 파일 단위로 처리하기 어려우면 보류 이유와 필요한 결정을 알리며 라인 분할안은 만들지 않습니다.
- 파일마다 완결된 `git add --` 명령을 한 줄씩 제공합니다. 이름 변경의 이전·새 경로와 삭제 경로도 현재 Git 상태에 맞게 처리하며, 설명·제외·보류 이유는 명령 블록 밖에 둡니다. 공백·특수 문자는 사용자의 shell과 Git 경로 해석에 맞게 처리합니다.
- staged·unstaged 상태와 현재 파일 내용을 구분합니다. 파일 전체를 staging하면 현재 작업 트리 내용으로 index가 갱신되므로 기존 staged 변경이 달라지거나 취소될 수 있습니다. 이 명령은 실제 staging이나 관리 파일 추적 해제를 수행하지 않습니다.
- 프로젝트 루트에서 현재 커밋할 그룹의 명령 줄만 복사해 실행하세요. 해당 커밋을 마친 뒤 다음 그룹으로 진행합니다. 설명·메시지가 포함된 파일 전체나 여러 그룹의 명령을 한꺼번에 실행하지 않습니다.
- 후보가 없으면 없음으로 보고합니다. 작성 중 변경이 추가되면 영향받은 부분을 다시 확인합니다. 실제 스테이징·커밋 전에도 현재 diff와 staged 내용을 목록에 대조하세요. 기존 staged 변경도 커밋에 포함될 수 있습니다. 목록 작성은 명령 실행이나 작업 수락을 뜻하지 않습니다.
