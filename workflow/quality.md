# 코드 품질·분야별 검증

개정: 2026-11-08 · 관리 구조 버전: `5`

## 코드 작성의 우선 원칙

이 절은 언어와 플랫폼에 관계없이 모든 코드의 신규 작성·수정에 공통 적용한다. 계획의 설계 기준, 실행의 구현·자체 검증, 통합의 수락 판단과 하위 에이전트 지시서에도 반영한다. 간소화, 시간·토큰 절약 또는 선택적인 성능 최적화와 충돌하면 다음 원칙을 우선한다.

1. **기능의 안정성과 정확성을 최우선으로 충족한다.** 정상 동작뿐 아니라 설계·규격과의 일치, 오류 처리와 중요한 경계 조건을 확인한다. 당장 동작한다는 이유로 설명되지 않은 이상 현상을 허용하지 않는다. 설계와 맞지 않는 임시 코드, 오류를 숨기는 조건문·마스킹, 근거 없는 지연·재시도로 증상만 덮지 않는다. 규격이나 확인된 원인에 근거한 우회 처리가 필요하면 적용 조건과 근거를 기록하고 검증한다.
2. **예상과 다른 동작은 원인을 규명한다.** 재현 조건, 기대값과 관측값, 설계·규격의 근거를 대조하고 가설과 확인된 사실을 구분한다. 예를 들어 하드웨어 레지스터의 reserved bit가 1로 읽히면 문제가 없어 보인다는 이유로 넘기거나 무조건 0으로 만들지 않는다. 해당 비트의 읽기·쓰기 규정, 리셋값, 칩 리비전·정오표와 접근 방식 등 관련 근거를 확인하여 규정된 동작인지 오류인지 원인을 설명한다. 원인과 무관한 포괄적 조사를 늘리지 않는다.
3. **원인 미확인을 해결 완료로 처리하지 않는다.** 현재 환경에서 규명할 수 없으면 확인된 사실, 남은 가설, 필요한 측정·사용자 테스트와 영향을 기록해 인계한다. 사용자 검증 대기 및 재시도 중단 규칙을 따르되, 단계 종료를 문제 해결이나 관련 기능의 수락 완료로 간주하지 않는다. 원인 규명을 이유로 접근 불가능한 환경을 임의로 구축하지 않는다.
4. **안정성 다음으로 Human Readable, Reusable, Portable을 우선한다.** 사람이 읽고 흐름을 이해하기 쉬운 구조, 필요한 범위의 재사용, 플랫폼 의존부의 분리를 선택적인 성능 최적화·코드 축약보다 우선한다. 가상의 미래 요구를 위한 과도한 추상화나 범용화는 피한다. 명시된 필수 실시간·메모리·성능 조건은 충족하되, 이 조건과 가독성·재사용성·이식성이 충돌하면 측정 근거와 대안을 제시하고 중요한 설계 변경은 사용자와 확인한다.
5. **이름만으로 역할과 동작 흐름을 이해할 수 있게 한다.** 변수는 담는 의미·상태·필요한 단위를, 함수는 수행 동작과 대상을 드러내도록 명명한다. 모호한 약어와 `data`, `temp`, `process` 같은 이름은 의미가 분명한 좁은 문맥 외에는 피한다. 기존 언어·프로젝트의 명명 관례 안에서 일관성을 유지하고, 긴 주석으로 모호한 이름을 보완하지 않는다. 비자명한 이유만 영어 주석으로 간결하게 남긴다.

## 9. 분야별 적용 기준

아래는 분야별 검증 대상이며 매번 전부 수행할 고정 목록이 아니다. 계획은 필수 목표, 실행은 방법을 정하고 통합은 유효한 근거를 재사용한다.

| 분야 | 기준과 검증 대상 |
|---|---|
| C | 플랫폼·컴파일러·링커·ABI, 메모리·시간 제약, 수명·경계·정의되지 않은 동작·동시성, 빌드와 대상 환경 통합 검증 |
| Rust | 타깃·툴체인·crate·feature·no_std, 공개 API·소유권·동시성·unsafe 근거·FFI, 빌드·테스트·통합 검증 |
| 문서 | 독자·목적·분량·용어·문체·서식·인용, 정확성·근거, 실제 렌더링과 전체 구성 |
| 조사·분석 | 질문·자료 범위·기준 날짜·출처 품질·방법·불확실성, 재현 가능성과 결론·근거의 연결 |
| 그 밖의 작업 | 수락 기준, 필요한 도구·환경, 실제 사용 조건에서의 검증 |

현재 환경에서 불가능한 검증은 사용자에게 인계하며 수행하지 않은 검증을 통과로 표시하지 않는다.

### Rust 테스트 코드와 최종 제출

- 사용자가 별도로 요구하지 않는 한 최종 제품 소스에 새로운 `#[cfg(test)]` 테스트 모듈·함수 및 테스트 전용 보조 코드를 추가하지 않는다. 기존 테스트는 이 규칙만을 이유로 삭제·이동하지 않는다.
- 같은 Cargo 패키지의 `src/`와 나란한 `tests/`에 통합 테스트를 두는 것은 허용한다. 필요한 검증이 있을 때 기존 구조를 우선 사용하고, 디렉토리가 없으면 필요한 범위에서 만들 수 있다. 허용은 디렉토리 생성 의무나 별도 `Cargo.toml`을 가진 테스트 패키지 생성 지시가 아니다.
- `tests/`는 제품 소스와 분리된 테스트 위치이지 자동 커밋 제외 대상이 아니다. 테스트의 최종 보존·커밋 포함 여부는 작업 범위와 저장소 규칙을 따른다. 테스트를 제외하도록 요청받으면 테스트 파일뿐 아니라 이번 작업의 테스트 전용 설정·의존성·잠금 파일 변경도 확인하며, 제품이나 기존 테스트에 필요한 변경까지 제거하지 않는다. 제외를 위해 기존 추적 파일이나 무시 설정을 임의로 바꾸지 않는다.
- 실행·통합의 내부 검증에는 임시 테스트 코드를 사용할 수 있다. 제출 전에 이번 작업의 임시 코드와 전용 설정·의존성을 정리하고, 재현에 필요한 검증 자료는 제품 소스와 분리하여 필요한 범위에서 보존한다. 통합의 임시 검증 허용은 제품 동작을 수정할 권한을 추가하지 않는다.
- 이 제한은 필수 검증을 생략하는 근거가 아니다. 대상 제품 코드 버전·검증 방법·결과를 기록하고, 임시 코드 정리 후 최종 제출 상태에서 관련 빌드·검사를 수행한다. 제품 코드가 바뀌면 영향받은 검증을 다시 수행한다. 통합 테스트 편의를 위해 비공개 구현을 임의로 공개 API로 바꾸지 않는다.
