# 기존 관리 구조 전환

개정: 2026-11-08 · 관리 구조 버전: `5`

### 관리 구조 버전 확인과 기존 프로젝트 전환

계획·통합 담당자는 요청된 프로젝트 작업을 시작·재개할 때 관리 구조를 확인한다. 개정 규칙을 새로 전달받은 기존 담당자도 구구조이면 아래 절차로 전환한다. 문서 자체 개정과 프로젝트 전환 요청의 구분은 [1절](common.md)을 따른다.

1. `index.md`의 `layout_version`과 실제 구조를 대조한다. 현재 버전은 `5`이며 워크플로우 개정 날짜와 별개다. 이미 일치하면 다시 개편하지 않는다. 표기가 없으면 실제 구조를 확인한다. 더 높은 버전이나 식별 불가능한 구조를 임의로 낮추거나 덮어쓰지 않는다. 새 프로젝트는 계획·통합 담당자가 현재 버전으로 생성한다.
2. 전환은 해당 계획·통합에 포함되는 관리 작업이다. 총괄 시작 시 전환이 필요하면 지정한 통합 담당자에게 이 관리 작업만 맡기고 인계를 확인한 뒤 실행 배정을 시작한다. 초기 계획이나 요구사항을 자동으로 새로 만들지는 않는다. 승인된 대상 프로젝트 내부의 전환에 별도 실행 단계나 반복 승인을 요구하지 않는다. 전환 담당자는 한 명으로 정한다. 진행 중인 실행·검토 담당자의 문서 갱신이 끝나고 경로 인계가 확인된 뒤 이동한다. 조정이 안 된 항목은 이동하지 않고 전환 대기 사유와 재개 조건을 남긴다.
3. 이동 전 기존 변경까지 보존할 수 있는 사본 또는 복구 가능한 버전을 확보한다. `migration.md`에 출발·목표 버전, 담당자, 시각, 전환 상태와 ID별 이전 ID·새 ID·이전 경로·이후 경로·상태 판단 근거·처리 여부를 기록한다. 기존 커밋에 없는 문서를 기존 커밋만으로 복구 가능하다고 판단하지 않는다.
4. 버전 4에서 전환할 때는 기존 ID·문서·폴더를 유지하고 이 절의 보존·담당 확인 아래 [11절](orchestration.md)의 의존 관계 항목과 필요한 운영 메타정보만 보완한다. 총괄을 호출하지 않았다면 자동 운영은 미시작으로 구분하며 가상의 실행 식별자·진행 이력을 만들지 않는다. 자동 실행을 시작하거나 현황판을 설치하지 않는다. 버전 1의 `tasks/`와 `revisions/`, 버전 2·3의 `work-items/`를 전환할 때는 결과 보고·수락 기록에 대조하여 분류한다. 상위 Task ID는 유지하고 하위 작업은 [4절](records.md)의 `<상위TaskID>-<TYPE>-<번호>`로 통일한다. 예: 기존 `R-T-01-01`은 `T-01-REV-01`로 바꾼다. 기존 `T-EXT-*`, `T-VAL-*` 또는 유형 없는 하위 ID는 문서의 목적·의존 관계로 상위 Task와 유형을 확인하며 숫자만 보고 추정하지 않는다. 상태가 불명확하거나 상위 Task·유형·새 ID가 확정되지 않으면 원위치에 보존하고 필요한 확인을 남긴다. 새 ID 충돌 시 덮어쓰거나 임의 재번호하지 않는다.
5. 지시서는 현재 상태에 맞는 `work-items/<status>/<새ID>.md` 한 원본으로 정리한다. 기존 `reports/`의 경로 형태와 관계없이 해당 작업의 최신 유효 보고 내용을 작업 문서 뒤의 수행 결과·검증 결과 절에 합치고, 이전 제출·반려·수락은 날짜·대상 버전·결정·이유를 담은 짧은 이력으로 정리한다. 기존 보고서의 고유한 근거와 원문은 확인된 복구 버전으로 보존하거나, 복구 버전이 없으면 `evidence/<상위TaskID>/<새ID>-legacy-report-<번호>.md`로 보존한다. 이는 과거 기록 보존용이며 새 제출마다 별도 보고서를 만드는 규칙이 아니다. 합친 내용과 복구 수단을 확인한 뒤에만 기존 보고서 원본을 정리한다.
6. 증빙은 `evidence/<상위TaskID>/`로 모으고 작업 문서·`index.md`·`plan.md`·`integration.md` 등 현재 참조의 ID·파일명·링크를 함께 갱신한다. 원래 요구사항·판단 근거·검증 이력·산출물 버전을 보존하며 실제로 수행하지 않은 검토나 수락을 추가하지 않는다. 과거 기록에 남는 이전 ID·경로는 대응표로 추적한다. 문서 이름이나 오래된 상태 표기만으로 완료를 추정하지 않는다.
7. 누락·중복, 원래 내용 보존, ID 대응, 현재 참조, 증빙 연결, 상태 근거·의존 관계와 담당 인계를 확인한다. 구버전에서 버전 5로 직접 전환하며 중간 버전 구조를 별도로 만들지 않는다. 모두 끝난 경우에만 `index.md`에 `layout_version: 5`와 전환 완료 시점·담당자를 기록한다. 구조 전환은 실행 결과의 새로운 수락이나 전체 완료를 뜻하지 않는다.
8. 중단되면 `migration.md`를 전환 중으로 두고 완료·미완료 항목을 구분한다. 재개 시 실제 파일과 대응표를 대조하여 남은 항목만 처리한다. 전환 중에는 관련 경로에 의존하는 쓰기를 보류하며 독립적인 읽기·조사는 계속할 수 있다. 불일치나 미확정 상태를 숨기려고 완료 버전을 먼저 기록하지 않는다.

실행 담당자는 프로젝트 전체 전환과 `index.md` 생성을 하지 않는다. 구구조·전환 중 상태를 발견하면 영향과 전환 필요성을 보고하고, 영향받는 작업의 재개 조건을 인계한다. 다른 위치의 기록 이동, 새 권한·비용 또는 실질적인 요구사항 변경이 필요하면 기존 승인 범위를 확인하고 필요한 결정만 요청한다.
