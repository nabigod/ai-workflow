# 프로젝트 구조·작업 상태·검증 기록

개정: 2026-11-08 · 관리 구조 버전: `5`

## 2. 시작과 운영 방식

목표, 범위, 완료 조건, 입력 자료, 작업 폴더와 산출물 위치를 기존 지시와 자료에서 확인한다. 계획에서는 [6절](planning.md)의 인터뷰로 요구사항의 모호함을 해소한다. 실행·통합에서는 확정된 요구사항 안의 구현·검증 방법을 판단하되, 요구사항의 누락·충돌을 발견하면 임의로 확정하지 않고 관련 작업을 보류하여 확인한다. 실행은 분야에 따라 구현·조사·작성·제작을 뜻한다.

### 수동 기본과 자동 운영의 구분

이 문서의 단계별 제작·검증·수락 기준은 두 모드에 공통으로 적용한다. 자동 모드는 승인 범위 안의 후속 단계 배정 권한만 추가하며, 완료 기준·수락 담당·권한 경계를 완화하지 않는다. 자동 운영의 시작·중지·재개는 [11절](orchestration.md), 현황판은 [12절](dashboard.md)을 따른다.

### 간소 방식

의존 관계가 단순하면 목표, 범위, 완료 조건, 결과물, 검증, 미해결 문제와 다음 조치를 짧게 기록한다. 관리 폴더를 일괄 생성하지 않는다. 다른 담당자에게 인계하거나 나중에 재개해야 하면 독립적으로 읽을 수 있는 짧은 작업 문서 하나에 지시와 결과 보고를 함께 남긴다. 사용자 메시지가 충분한 간소 단독 실행에서는 별도 지시서 없이 진행할 수 있다.

기록량과 실행 담당은 독립적으로 선택한다. 간소 방식에서도 담당·모델 배정은 [담당·소유권](common.md)·[모델·재시도](models.md)을 따르며 다음 단계로 자동 전환하지 않는다.

이미 표준 방식인 프로젝트는 일부 작업이 작다는 이유로 기록을 우회하지 않는다. 같은 구조 안에서 변경된 항목만 갱신하고 중복 보고를 생략한다. 의존 관계·담당자·인계가 늘어나면 기존 기록을 이어받아 표준 방식으로 전환한다. 실행 담당자는 전환 필요성을 보고하며, 프로젝트 전체 구조의 생성·전환은 계획·통합 담당자가 맡는다. `index.md` 갱신 권한은 [담당·소유권](common.md)·[모델·재시도](models.md)을 따른다.

### 표준 방식과 프로젝트 경계

여러 산출물, 복잡한 의존 관계, 병렬 작업 또는 장기 인계가 있으면 아래 구조를 사용한다. 실제 필요한 문서와 상태 디렉토리만 만든다.

사용자가 지정한 프로젝트 루트의 `.ai-work/<project-id>/`를 기본 위치로 사용한다. 생성 전에 대상 파일과 프로젝트 구조로 루트를 확인한다. 저장소 루트는 판단 근거로 쓰되 사용자가 명시한 경계를 우선한다. 현재 실행 디렉토리, 에디터·에이전트의 설치·설정 폴더, 스킬 파일 위치를 자동으로 프로젝트 루트로 간주하지 않는다. 후보가 여러 개이고 대상이 불명확할 때만 확인한다.

프로젝트가 없는 대화에서는 환경이 제공하는 사용자 접근 가능한 작업·출력 폴더에 기록한다. 적절한 위치를 확인할 수 없을 때만 묻는다. 생성한 문서에는 사용자가 열 수 있는 절대 경로나 파일 링크를 제공한다. 저장이 불가능하면 내용을 대화로 제공하고 저장했다고 보고하지 않는다.

기존 기록을 먼저 확인해 중복 프로젝트를 만들지 않는다. 기존에 다른 이름이나 위치의 기록이 있으면 알리고 임의 이동·중복 생성을 하지 않는다. [구조 전환 규칙](migration.md)에 따른 대상 프로젝트 내부의 구구조 개편은 명시적 예외다. 다른 프로젝트나 별도 관리 위치까지 범위를 확대하지 않는다. `project-id`는 짧고 고유하게 정하고 유지한다.

```text
.ai-work/<project-id>/
├── index.md
├── plan.md
├── work-items/
│   ├── 00-planned/
│   ├── 10-ready/
│   ├── 20-in-progress/
│   ├── 30-review-pending/
│   ├── 40-in-review/
│   ├── 50-changes-requested/
│   ├── 60-blocked/
│   ├── 90-done/
│   └── 99-cancelled/
├── evidence/
│   └── T-01/
│       ├── T-01-external-evidence-01.md
│       └── T-01-VAL-01-test-log-01.txt
├── integration.md
├── migration.md
├── summary.md
└── dashboard/
    ├── index.html
    └── status.json
```

- `work-items/`: 상위 Task와 하위 작업을 같은 상태 체계로 관리한다. 작업마다 `<ID>.md` 하나에 지시·수행 결과·검증 결과·제출 및 검토 이력을 함께 기록한다. 이 문서에서 작업지시서와 결과 보고는 같은 파일 안의 해당 절을 뜻한다. 식별·상태 규칙은 [4절](records.md)을 따른다.
- `90-done/`: 통합 담당자가 수락한 작업 문서를 보관한다. 완료 후에도 문서는 `work-items/` 아래에 남는다. 별도 `reports/`와 `99-archive/`는 만들지 않는다.
- `evidence/`: 로그·관찰 결과·시험 자료 등 증빙을 상위 Task별 고정 폴더에 둔다. 예를 들어 `T-01`, `T-01-REV-01`, `T-01-EXT-01`, `T-01-VAL-01`의 증빙은 모두 `evidence/T-01/`에 저장한다. 증빙은 작업 문서에서 연결하며 별도의 작업 상태를 갖지 않는다. 수행 결과 요약을 증빙 폴더에 중복 작성하지 않는다.
- `index.md`: 기준과 운영 요약이다. 갱신 권한은 [담당·소유권](common.md)·[모델·재시도](models.md), 기록 항목과 현재 상태의 해석은 [4절](records.md)을 따른다.
- `plan.md`: 요구사항, 공통 설계·기준과 사용자 결정을 관리한다. 작업별 상세 지시·결과는 해당 작업 문서로 연결한다.
- `integration.md`: 작업 간 연결, 추가 검증과 범위 전체의 판단을 기록한다. 개별 작업의 결과·검증표·수락 이력을 복제하지 않고 해당 제출·판정으로 연결한다.
- `dashboard/`: 별도 제작·검증된 읽기 전용 현황판을 사용할 때만 생성한다. `index.html`은 화면, `status.json`은 원본 문서와 실행 정보에서 만든 표시용 스냅샷이다. 현황판이 없다고 버전 5 전환이나 수동 운영이 실패한 것은 아니다.
- `migration.md`: 구조 전환 때만 생성한다. `summary.md`는 전체 완료 때만, `99-cancelled/`는 실제 취소 항목이 있을 때만 만든다.

소스와 최종 산출물은 프로젝트의 적절한 위치에 저장하고 관리 문서에서 연결한다. 작업 문서의 상태 이동은 [4절](records.md)을 따르며, 증빙과 최종 산출물은 고정 위치에 유지한다. 임시 로그와 대용량 중간 파일은 별도로 관리한다.

Git 제외·언어 기준은 [공통 규칙](common.md)을 따른다.

### 파일·디렉토리 명명 규칙

- 커밋 도구와 실행 환경에 따른 문자 인코딩 문제를 줄이기 위해 `.ai-work/` 아래에 새로 생성하는 모든 파일·디렉토리 이름에는 한글을 사용하지 않는다. 이름은 ASCII 영문자·숫자·하이픈(`-`)·밑줄(`_`)·마침표(`.`)만 사용한다. `project-id`와 작업 ID에도 이 규칙을 적용한다.
- 작업 문서의 ID·파일명·단일 원본·상태 위치는 [4절](records.md)을 따른다.
- 증빙 파일은 작업 문서와 구분하여 `<작업ID>-<evidence-type>-<번호>.<확장자>`로 명명한다. `evidence-type`은 `external-evidence`, `test-log`처럼 소문자 영문과 하이픈을 사용하며 같은 종류에 같은 이름을 쓴다. 예: `evidence/T-01/T-01-external-evidence-01.md`, `evidence/T-01/T-01-REV-01-test-log-01.txt`. 번호는 작업 ID와 증빙 종류별로 부여하며, 기존 판정에서 참조한 증빙을 덮어쓰지 않는다.
- 특정 작업 ID에 속하지 않는 공통 관리 문서는 `index.md`, `plan.md`, `integration.md`, `migration.md`, `summary.md`처럼 역할을 나타내는 고정 영문 이름을 사용한다. 그 밖의 공통 자료도 ASCII 영문 이름을 사용한다.
- 파일명 제한은 문서 내용의 언어 제한이 아니다. 문서 언어는 [공통 언어·주석 규칙](common.md)을 따른다.
- 기존 파일명·ID·보고서 구조의 변경은 [구조 전환 절차](migration.md)에 따라 담당 인계·복구 수단·참조 경로를 확인한 뒤 수행한다. 워크플로우 문서 개정만으로 기존 프로젝트 파일을 일괄 이동하지 않는다.

### 시작·재개 시 읽기 순서

프로젝트 경계와 관리 구조를 확인한 다음 `index.md`, 대상 ID의 현재 작업 문서 안의 지시·최신 수행 결과·검증 결과·최신 제출 및 판정·이후 미제출 변경, 필요한 증빙·선행 결과물·공통 기준 순서로 읽는다. 이전 이력은 재시도 누계, 현재 판정의 근거 또는 변경 영향 확인에 필요한 범위에서 읽는다. `index.md`가 오래됐으면 현재 위치와 해당 버전의 근거를 직접 확인한다. 모든 완료 작업이나 과거 로그를 매번 읽지 않는다.

공통 권한·품질·상태·검증 규칙은 모든 담당자에게 적용한다. 단계별 상세 절차는 현재 단계와 인계에 필요한 부분을, 구조 전환·자동 운영·현황판 규칙은 해당 조건에서 읽는다. 현재 컨텍스트에 남아 있는 확인 자료는 변경되거나 구체적인 의심이 생긴 경우에만 다시 읽는다. 제목·항목 ID로 필요한 절을 좁혀 읽고, 로그는 판정에 필요한 구간부터 확인하되 원인·문맥이 불분명하면 범위를 넓힌다. 새 담당자·컨텍스트 복구의 읽기는 [진입 규칙](entry.md)을 따르며 요약이 필수 원자료 검토를 대신하지 않는다.

구조 전환이 필요한 계획·통합 담당자는 [구조 전환](migration.md)을 읽는다.

## 4. 작업 식별, 현황과 상태

이 절이 작업 상태와 이동 권한의 공통 기준이다. 각 단계는 이를 참조하며 별도 상태 체계를 만들지 않는다. 간소 단독 실행도 같은 상태 의미를 쓰되 디렉토리 생성을 강제하지 않는다.

### 작업 ID와 하위 작업 유형

- 상위 Task ID는 `T-<번호>`, 하위 작업 ID는 `T-<상위번호>-<TYPE>-<하위번호>`로 통일한다. 예: `T-01`, `T-01-REV-01`, `T-01-EXT-01`, `T-01-VAL-01`. 파일명·본문·작업 지시·의존 관계에서 같은 ID를 사용하며 관련 ID는 항상 상위 Task ID로 시작한다.
- 유형은 다음 대문자 코드를 사용한다. 같은 의미에 다른 약어나 소문자를 혼용하지 않는다.

| TYPE | 의미 | 적용 범위 |
|---|---|---|
| `REV` | 수정 작업 | 기존 작업의 완료 조건 미충족이나 확인된 결함을 수정 |
| `EXT` | 외부 환경 작업 | 별도 환경·장비·접근 조건에서 수행할 작업 |
| `VAL` | 검증 작업 | 명시된 기준에 대한 시험·검증 결과를 제출 |

- 검증 자체가 목적이면 수행 환경이 외부여도 `VAL`을 사용하고 환경 조건을 본문에 적는다. 별도 환경 준비·접근 확보 등의 작업은 `EXT`로 구분한다. 단순 사용자 테스트 대기만으로 새 작업을 자동 생성하거나 실행하지 않는다.
- 상위 Task 번호는 프로젝트 안에서, 하위 번호는 상위 Task와 TYPE의 조합별로 순차 부여하며 재사용하지 않는다. 기본은 두 자리 숫자(`01`, `02`)를 쓰고 기존 프로젝트의 번호 자릿수는 유지한다. 재제출·상태 이동만으로 ID를 바꾸지 않는다.
- 하위 작업을 다시 수정하더라도 유형·번호를 중첩하지 않는다. 예를 들어 `T-01-VAL-01`을 수정하는 작업은 다음 사용 가능한 `T-01-REV-<번호>`를 부여하고, 수정 대상 ID에 `T-01-VAL-01`을 명시한다.
- 새 유형이 필요하면 계획·통합 담당자가 중복되지 않는 대문자 영문 코드와 의미·적용 기준을 `plan.md` 또는 공통 기준에 먼저 정의한다. 실행 담당자가 같은 의미의 유형을 임의로 만들지 않는다.
- 여러 Task에 영향을 주는 하위 작업은 책임지는 상위 Task 하나를 정하고 나머지는 관련 작업 ID로 연결한다. 같은 작업 문서를 여러 상위 Task에 복제하지 않는다. 모든 하위 작업은 자체 완료 조건과 상태를 가지며, 하위 작업의 수락만으로 상위 Task가 자동 완료되지는 않는다.

### 식별자와 지시서 메타정보

- 작업 문서의 파일명은 확장자를 제외하고 작업 ID만 사용한다. 예: `T-01.md`, `T-01-REV-01.md`, `T-01-EXT-01.md`, `T-01-VAL-01.md`. 제목·설명·상태·날짜·제출 회차는 파일명에 덧붙이지 않는다. 작업 제목은 문서 내부 제목에 기록한다.
- 원본 경로는 `work-items/<status>/<ID>.md`다. 간소 방식에서도 문서를 만들면 같은 파일명·단일 원본 원칙을 적용하되 상태 디렉토리 생성은 강제하지 않는다.
- 생성 담당자는 ID 중복을 확인한다. 지시서 보완만으로 ID를 바꾸지 않으며 독립적인 새 수정 요구에만 새 `REV` ID를 배정한다.
- 문서 상단에 ID, 요구사항 ID, 지시서 개정, 현재 담당자, 갱신 시각, 다음 조치·담당자, 최신 제출 시각·산출물 버전을 둔다. 관련된 경우 상위 Task ID, 수정 대상 ID, 연결된 하위 작업 ID, 증빙 경로, 대기 사유·해제 조건을 추가한다. 미제출 항목은 미제출로 표시한다. 본문에 중복된 현재 상태 필드는 두지 않는다.
- 실질 내용 개정과 담당·위치 등 운영 갱신을 구분한다. 요구사항·범위·수락 기준이 바뀌면 지시서 개정을 올리고 영향을 평가한다. 단순 이동만으로 지시 내용이나 산출물 버전이 바뀐 것으로 취급하지 않는다.
- 명령·의존 관계는 ID로 식별하고, 관리 운영 대화에서는 ID와 현재 파일 링크를 함께 제공할 수 있다. 일반 사용자용 결과물에는 이를 기본 노출하지 않는다. 경로가 사라지면 먼저 ID로 현재 위치와 전환 대응표를 찾는다. 중복 원본이나 빈 대체 문서를 생성하지 않는다.

### 작업 문서 내부 구성과 이력

1. **작업 지시:** [6절](planning.md)의 필수 내용을 기록한다.
2. **수행 결과:** 변경한 결과물의 역할·경로, 주요 결정과 후속 영향, 실제 입력·산출물 버전, 진행 상황·다음 조치를 적는다. 최신 제출 이후 미제출 변경과 요청·실제 모델 설정을 구분한다. 상단 메타정보와 같은 값은 반복하지 않는다.
3. **검증 결과·미해결 문제:** 항목별 상태·대상 버전·근거와 증빙 링크·남은 위험·사용자 검증 요청을 적는다.
4. **제출·검토·상태 이력:** 제출, 반려, 재제출, 수락 및 상태 이동을 짧게 누적한다. 시각·담당자·지시서 개정·대상 산출물 버전·판정과 이유를 남기고, 상태 이동 시 이전·이후 상태도 기록한다.

- 착수·상태 이동·제출·판정·막힘·중지·중요 결정 변경 때 바뀐 메타정보·결과 항목만 부분 수정하고 필요한 이력만 추가한다. 변하지 않은 지시·표·결과를 매번 다시 생성하거나 도구 호출마다 보고하지 않는다. 편집 후 변경 부분과 관련 참조를 확인한다.
- 최신 결과는 짧은 항목·검증표로 유지하되, 변경점만 나열하여 과거 대화를 재구성해야 하는 문서로 만들지 않는다. 이전 제출·판정 이력은 보존하고 당시 근거를 현재 상태에 맞춰 다시 쓰지 않는다. 정정·재제출은 바뀐 근거를 추가하며 동일 버전의 제출은 시각으로 구분한다.
- 상세 로그는 증빙에 두고 문서에는 조건·결론·근거 위치만 남긴다. 근거는 [5절](records.md)의 고정 증빙이나 복구 가능한 버전으로 연결한다. 회차별 보고서·별도 압축본은 만들지 않는다. `index.md`에는 운영 요약, `integration.md`에는 연결 검증·전체 판단만 갱신하고 개별 상세 결과는 원본으로 연결한다.
- 실행·사용자검증 담당자는 자기 수행 결과를, 통합 담당자는 자신의 판정을 기록한다. 문서 소유권과 필수 인계 정보는 [공통 규칙](common.md)을 따른다.

정상 흐름은 `계획됨 → 준비됨 → 진행 중 → 검토 대기 → 검토 중 → 완료`다. 준비됨은 자동 실행 허가가 아니다. 계획 산출물 자체의 완료는 계획 담당자가 판정하지만, 지시서 작성 완료를 이유로 실행 Task를 `90-done`에 넣지 않는다.

### 이동 권한과 예외 흐름

- **계획 담당:** 일반 Task를 생성하여 조건에 따라 계획됨·준비됨으로 둔다. 최신 제출 상태를 기준 문서에 반영할 수 있으나 실행 결과의 수락·재수락을 대신하지 않는다.
- **실행 담당:** 자기 지시서의 시작 조건을 확인하여 준비됨·진행 중으로 이동하고, 자체 검증과 보고 제출 후 검토 대기로 이동한다. 자기 수행 범위에서 확인한 수정 필요·막힘도 기록할 수 있다. 자체 검토는 진행 중에 포함하며 검토 중·완료로 이동하지 않는다.
- **사용자검증 담당:** 수동 `[사용자검증]` 요청에 따라 소유권을 인계받은 기존 작업 문서의 사용자 검증 항목·근거·이력만 갱신한다. 제출된 작업은 기본적으로 검토 대기를 유지한다. 항목 통과는 작업 완료가 아니며 `90-done`으로 이동할 수 없다. 미완료 기준이나 결함을 확인하면 해당 항목을 실패로 기록하고, 수정 필요가 확인된 범위에서는 작업을 `50-changes-requested`로 둘 수 있다. 관련 REV의 생성·지시는 계획·통합 담당자의 권한에 남고, 완료 작업의 기존 수락 판정을 변경하는 권한은 통합 담당자에게만 있다. 수락 재검토가 필요하면 통합 담당자에게 인계한다.
- **통합 담당:** 제출물을 확인하고 검토 대기에서 검토 중으로 이동한다. 결과에 따라 완료·수정 필요로 이동하거나 외부 검증·추가 입력을 기다리면 검토 대기로 돌리고 다음 행동을 명시한다. 수정 지시서는 계획됨 또는 준비됨으로 생성한다. 수동 모드에서는 별도 실행 요청을 기다리고, 자동 모드에서는 총괄이 승인 범위와 시작 조건을 확인한 뒤 배정한다.
- **막힘 해제:** 해제 근거와 입력 버전을 확인한다. 아직 제작 중이면 준비됨으로, 유효한 결과물을 제출했고 검토만 남았으면 검토 대기로 돌린다. 현재 해당 단계의 담당자가 처리한다. 수동 모드에서는 다른 단계를 자동 시작하지 않으며, 자동 모드에서는 유효한 총괄 배정과 시작 조건을 다시 확인한다.
- **수정 재실행:** 수동 모드의 별도 실행 요청 또는 자동 모드의 유효한 총괄 배정과 시작 조건 확인 후 수정 필요에서 준비됨·진행 중으로 이동할 수 있다. 연결된 수정 작업이 있으면 수정 범위와 담당을 확인하고 원래 Task와 중복 실행하지 않는다.
- **완료 후 문제 발견:** 통합 담당자는 재검토가 필요한 작업을 검토 대기로, 수정이 확정된 작업을 수정 필요로 돌리고 이전 수락 버전과 이유를 남긴다. 실행·계획 담당은 발견 근거와 변경 제안을 보고하며 수락 기록을 임의로 덮어쓰지 않는다.
- **취소·대체:** 명시된 취소 또는 승인된 범위 변경 근거를 남긴다. 해당 단계 총괄 담당자가 진행 중 담당자와 인계를 마친 뒤 취소됨으로 이동한다. 대체 작업 ID를 연결하며 원래 요구사항의 제외·대체 승인도 별도로 확인한다. 취소는 수락 완료가 아니다.

상태를 바꿀 때 근거·담당·다음 행동을 갱신하고 같은 작업 안에서 파일을 이동한 뒤 원본이 하나인지 확인한다. 중단으로 위치와 이력이 어긋나면 마지막으로 완료된 전환과 실제 근거를 대조해 현재 담당자가 복구한다. 근거가 부족하면 임의 확정하지 않고 관련 작업을 보류한다. 디렉토리 이름만으로 검증 통과나 수락을 추정하지 않는다.

### Task와 수정 작업(REV)의 관계

원래 Task `T-03`에 수정이 필요하면 `50-changes-requested/`에 두고 수정 작업 `T-03-REV-01`을 연결한다. 수정 작업은 독립된 상태 흐름과 작업 문서를 가지며 결과 보고도 그 문서에 기록한다. 수정 실행 중 원래 Task까지 진행 중으로 함께 옮기지 않는다.

수정 작업 제출 시 실행 담당자는 수정 작업만 검토 대기로 이동한다. 통합 담당자는 수정 자체의 완료 조건과 원래 Task의 영향받은 조건을 확인하여 각각 판정한다. **수정 작업 수락은 원래 Task의 자동 완료가 아니다.** 원래 Task의 필수 수정·검증을 모두 충족해야 재수락한다. 연결된 수정이 검토 단계에 도달하면 원래 Task도 검토 대상으로 전환할 수 있으나, 미해결 수정이 남으면 수정 필요 또는 검토 대기 사유를 유지한다.

같은 수정의 재제출은 이 절의 개정·이력 규칙을 따른다. 별개의 수정 요구는 새 REV를 배정해 원래 Task와 관련 수정에 연결한다.

### 현재 상태와 기록의 관계

- 작업의 운영 상태는 원본 작업 문서의 유일한 현재 위치다. 수행·검증 결과는 최신 요약이고 제출·판정 이력은 당시 버전의 기록이다. 폴더 이름만으로 검증 통과나 수락을 추정하지 않는다.
- `index.md`는 마지막 운영 판단과 한정 갱신 시점의 요약이다. 구조 버전, 갱신 시각·담당자, 목표, 선택 단계·대상, 주요 결정, 작업별 ID·제목·기준 상태·담당·현재 문서 링크·다음 조치를 둔다. 버전·증빙·모델·의존 관계 상세는 작업 문서에 연결하고 배정에 필요한 조건만 요약한다. 자동 모드는 [11절](orchestration.md)의 운영 항목을 추가한다.
- 실행 중 변경은 자기 작업 문서에 남긴다. `index.md`는 [담당·소유권](common.md)·[모델·재시도](models.md)의 권한에 따라 계획·통합의 다음 판단 시점, 사용자검증의 현황·다음 조치 변경 시점, 총괄의 배정·결과 수신·중지 시점에 반영한다. 수행하지 않은 검토·수락은 기록하지 않는다.
- 검증 항목 통과, 작업 수락, 단계 종료, 프로젝트 전체 완료와 에이전트 실행 상태를 구분한다. 상태 폴더나 `index.md`는 실시간 생존 신호가 아니며 오래된 시각만으로 담당을 빼앗거나 재시작하지 않는다.
- 사용자 중단·보류 요청에는 현재 결과물·버전·근거, 미제출 변경·남은 입력과 다음 행동을 남기고 멈춘다. 보류를 실패·취소로 바꾸지 않는다. 명시적 재개 요청 후 담당·문서·실제 버전을 확인하며, 단순 결과 제출을 재개 허가로 간주하지 않는다. 총괄의 실제 실행 중단·재개는 [11절](orchestration.md)을 따른다.

## 5. 검증 인계와 입력 버전

### 검증 상태와 근거

검증 항목별 상태는 `통과`, `실패`, `미수행`, `사용자 검증 대기`, `해당 없음`으로 기록한다. 필수 여부, 대상 버전, 시험 조건, 수행 주체, 근거·증빙 또는 미수행 사유를 남긴다. `해당 없음`에는 적용되지 않는 이유가 필요하며 필수 항목을 임의로 제외하는 수단으로 쓰지 않는다. 필수 검증이 남거나 근거가 부족한 작업은 수락할 수 없다.

검증 결과는 해당 작업 문서의 최신 결과와 이력에 반영하고, 증빙은 [2절](records.md)의 상위 Task별 고정 경로에 보존한다. 다른 담당자나 사용자가 수행한 결과를 자신의 시험처럼 기록하지 않는다. 통합에서 별도로 전달받은 결과는 작업 문서의 검토 이력 또는 `integration.md`에 출처·조건·버전과 근거를 연결한다.

### 사용자 시험 대기와 인계

- 접근할 수 없는 보드·계측 장비·분리된 환경의 검증은 사용자에게 인계한다. 기존에 허용된 환경은 사용할 수 있으나, 새 환경 설치·보드 제어·원격 연결·별도 시험은 명시적 실행 요청 또는 확정 계획과 유효한 총괄 범위가 있어야 한다. 사용자 검증 대기는 추가 환경 준비의 승인이 아니다.
- 가능한 나머지 검증을 마친 뒤 대상 결과물·버전, 준비 조건, 짧은 절차, 기대 결과·실패 기준과 회신할 자료를 전달하고 현재 단계를 종료한다. 제출물이 있고 사용자 시험만 남으면 작업은 검토 대기, 항목은 사용자 검증 대기다. 제작 자체가 외부 조건으로 불가능하면 막힘이다.
- 사용자가 순차 안내를 원하면 [13절](user-validation.md)의 `[사용자검증]`으로 진행한다. 결과와 `[통합]` 요청을 함께 주면 통합 담당자가 직접 검토할 수 있다. 유효한 자동 모드에서는 총괄이 통합 검토를 배정하고 독립 작업의 진행 여부를 판단한다. 단계를 넘어 사용자 응답을 반복 조회하거나 환경을 자동 구축하지 않는다.

### 버전 식별과 검증 재사용

- 지시에는 입력 기준 버전을, 결과에는 실제 입력·산출물 버전을 기록한다. 커밋, 문서 개정, 저장 시점 또는 필요한 해시로 식별하며 같은 경로를 같은 내용으로 가정하지 않는다.
- 통합 판정은 작업 ID·제출 시각·산출물 버전으로 특정한다. 증빙은 고정 경로나 복구 가능한 버전에 연결한다. 제출·정정·재제출 이력과 미제출 변경 표시는 [4절](records.md)을 따른다.
- 지시·선행 산출물·공통 기준·인터페이스가 바뀌면 영향받는 작업과 기존 검증의 유효성을 평가한다. 운영 갱신과 실질 변경을 구분하고, 영향 평가 전의 산출물을 후속 작업의 확정 입력으로 쓰지 않는다. 선행 산출물 변경과 통합 판정의 유효성은 통합 담당자가 판단한다.
- 대상 버전·시험 조건·근거가 유효한 검증은 재사용한다. 변경 영향, 연결 부분, 누락된 필수 항목과 구체적 미해결 위험에만 추가 검증하며 새로운 근거 없이 전체 시험을 반복하지 않는다. 과거 수락을 새 버전에 자동 적용하지 않는다.
- 사용자 결과의 버전·조건이 다르거나 근거가 불충분하면 통과 처리하지 않고 필요한 확인만 요청한다. 시작 조건에 통합 수락이 명시된 경우 자체 검증으로 대신하지 않는다.
