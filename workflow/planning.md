# 계획

개정: 2026-11-08 · 관리 구조 버전: `5`

## 6. [계획]

### 입력과 수행

프로젝트 목표, 요구사항, 제약과 관련 자료를 입력으로 사용하며 고정된 형식을 요구하지 않는다. 새로운 구현사항이나 중요한 재계획의 요구사항은 아래 인터뷰 기준으로 확인한다.

1. 프로젝트와 입력을 확인하고 [2절](records.md)에 따른 관리 구조 전환을 먼저 마친다.
2. 아래 인터뷰로 목표·필수 요구사항·품질 제약·제외 범위·완료 조건을 확정하고 요구사항 ID를 부여한다. 주요 위험과 필수 검증 목표를 정하되 세부 방법은 필요한 경우에만 고정한다.
3. 기능·책임·입출력·공유 자원으로 실행 단위를 나눈다. 수정·검증 범위, 선행 조건과 통합 지점을 정한다. 최초 계획에서 각 작업의 병렬 가능 여부·근거·조건을 판단하여 아래 필수 항목에 따라 작업지시서에 남긴다. 명명·용어·문체·데이터 형식·공개 인터페이스 등 공통 기준을 실행 전에 정한다.
4. 읽을 자료량, 예상 변경량, 검증 난도와 외부 의존성으로 작업량을 소·중·대로 평가하고 컨텍스트 분할 필요성을 판단한다. 토큰 추정은 측정 가능하거나 한도 판단에 필요한 경우에만 근거와 오차를 붙인다. 역할별 지정 모델을 전제로 작업 분할·입력 보완·검증 방법을 정하며, 예상 난도를 이유로 최초 배정 단계를 높이지 않는다.
5. 표준 방식은 `plan.md`, `work-items/<status>/<ID>.md`와 `index.md`를 작성·갱신한다. 지시서는 계획됨 또는 준비됨에 둔다. 간소 방식은 같은 핵심 정보를 짧은 계획·인계 지시서로 남긴다.
6. 요구사항과 작업의 대응, 새 담당자가 지시서와 참조 자료만으로 시작할 수 있는지를 검토한다. 기존 실행 결과는 제출 상태로 반영할 수 있으나 통합 수락을 대신하지 않는다.

### 계획 인터뷰

- 기존 사용자 답변과 입력 자료를 먼저 확인한다. 자료로 해소되지 않는 요구사항의 모호함은 질문하며, 이미 확정한 사항을 반복 질문하지 않는다.
- 계획에 미치는 영향이 큰 순서로 한 번에 1~3개씩 질문한다. 가능한 경우 선택지·권장안·선택에 따른 차이를 함께 설명하고, 답변에 따라 남은 모호함만 추가 확인한다.
- 확정된 요구사항 안의 구현 세부는 AI가 결정한다. 외부 동작·공개 인터페이스·비용·수락 기준을 바꾸는 선택은 요구사항 결정으로 취급한다. 사용자가 특정 판단을 위임하면 그 범위에서 결정하고 근거를 남긴다.
- 답변을 기다리는 동안 독립적인 자료 조사·현황 확인은 진행할 수 있다. 미확정 답변에 의존하는 설계·작업지시서는 확정하지 않으며 무응답·시간 경과를 동의로 간주하지 않는다.
- 확정된 결정과 남은 질문은 기존 계획 기록에 반영한다. 인터뷰 전문이나 별도 문서를 기본적으로 만들지 않는다. 요구사항의 모호함이 해소되거나 사용자가 판단을 위임한 경우 계획을 확정한다. 답변이 없으면 미확정 부분과 재개 조건을 인계한다.

### 작업지시서 필수 내용

아래 항목은 정보의 충족 기준이며 각각을 별도 절로 늘릴 필요는 없다. 관련 항목은 짧게 묶고 공통 기준은 원본 경로·절·버전으로 참조한다. 작업별 목표·범위·완료 조건과 예외는 구체적으로 남기며, 미확정 조건을 생략해 시작 가능한 것처럼 보이게 하지 않는다. 빈 템플릿이나 모든 선택 항목을 일괄 생성하지 않는다.

- [4절](records.md)의 식별·운영 메타정보, 담당 요구사항 ID와 목적.
- 목표, 포함·제외 범위, 결과물 위치, 수정 가능한 대상과 금지 범위.
- 입력·기준 버전, 접근 조건, 배경과 사용자 결정·위임받은 판단.
- 선행 작업 ID·필요한 수락 및 검증 조건·사용할 산출물 버전·시작 조건, 수정 가능한 파일·공유 자원 소유권, 인터페이스·데이터 형식, 관련·필수 하위·후속 작업. 해당 없는 조건과 미확정 조건을 구분하고 제목·번호만으로 추정하지 않는다. 자동 배정 시 확인 절차는 [11절](orchestration.md)을 따른다.
- 병렬 가능 판단(`가능`·`조건부 가능`·`불가`), 함께 수행할 수 있는 작업 ID 또는 그룹, 근거·선행 조건·동시 수행 금지 대상·통합 순서. 코드·관리 문서뿐 아니라 공통 설정·잠금 파일·빌드 출력·Git index·시험 장비 등 공유 자원의 소유권과 입력 버전 안정성도 확인한다. 조건부 가능은 해제 조건을 명시하며, 미확정이면 병렬 가능으로 간주하지 않는다. 별도 병렬 원장 없이 기존 작업지시서에 기록한다.
- 중요한 제약·위험, 수행 지침, 완료 조건별 필수 검증 목표·근거 형태와 실행 담당자가 선택할 수 있는 방법의 범위.
- 환경 때문에 수행할 수 없는 검증과 영향, 작업량·분할 판단, 역할별 지정 모델과 사용자 명시 예외. 재시도 작업은 동일 문제의 실패 근거·누적 횟수·남은 상향 한도를 연결하며 계획·통합의 판단만으로 최초 모델 단계를 높이지 않는다.
- 검토 담당과 다음 단계에 넘길 정보. 결과 기록·증빙 위치는 [2절](records.md)·[4절](records.md)·[5절](records.md)의 공통 규칙을 참조하며 작업별 예외만 추가한다.

### 종료 조건

인터뷰 종료 조건, 요구사항 대응과 실행 가능한 지시서를 확인하고 경로·의존 관계·사용자 결정을 인계한다. 미확정 요구사항이 남은 부분은 계획 완료나 실행 준비됨으로 표시하지 않는다. 계획 산출물의 완료와 실행 작업의 준비 상태를 구분하며 제작·구현은 시작하지 않는다.
