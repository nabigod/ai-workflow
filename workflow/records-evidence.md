# 테스트케이스·증빙·입력 버전

개정: 2026-11-17 · 관리 구조 버전: `5`

## 5. 테스트케이스 원본

완료 조건은 해당 작업 문서의 TC가 단일 원본이다. 계획·REV 작성자는 요구사항마다 확인 가능한 정상·오류·경계 조건을 필요한 범위에서 정의한다. 사례를 늘리기 위한 분할이나 구현 내용을 그대로 반복하는 시험은 만들지 않는다. 문서 검토·관찰·사용자 시험도 TC가 될 수 있으며 자동 테스트 코드 작성을 일괄 강제하지 않는다.

| 항목 | 기록 기준 |
|---|---|
| 식별 | 작업 안에서 고유하고 재개해도 유지되는 TC ID, 요구사항 ID |
| 완료 조건 | 필수 여부, 준비 조건/입력, 수행 행동, 관측 가능한 기대 결과 |
| 검증 | 방법·수행 주체, 상태, 대상 산출물 버전, 근거/증빙 또는 미수행 사유 |

ID는 `T-01-TC-01`처럼 Task와 함께 유일하게 식별한다. 기존 안정적인 ID가 있으면 유지한다. 최초 상태는 미수행, 미제출 버전/근거는 미제출·없음으로 표시한다. 공통 조건은 표 위에 한 번 쓰고 예외만 항목에 적을 수 있다. 기준 변경은 지시서 개정과 영향을 기록하며 같은 케이스의 재시험으로 ID를 늘리지 않는다. 항목을 삭제해 미완료를 숨기지 않고 취소·대체 이유/승인을 남긴다.

상태는 `통과`, `실패`, `미수행`, `사용자 검증 대기`, `해당 없음`이다. 해당 없음에는 근거가 필요하며 필수 조건을 임의 제외할 수 없다. 통과에는 해당 버전·시험 조건의 유효한 근거가 필요하고 실행하지 않은 검증을 통과로 쓰지 않는다. 필수 검증이 남거나 근거가 부족하면 수락할 수 없다. 다른 담당자·사용자가 수행한 결과는 출처를 명시한다. 실행은 자기 결과, 통합은 자신의 판정만 기록한다.

## TC 현황 조회

어떤 역할·별도 에이전트에서 요청해도 다음 기준을 사용한다. 현재 명령의 쓰기·수락 권한은 추가되지 않는다.

1. 요청 범위·기준 시각/버전과 원본 작업 문서를 정한다. index는 위치 안내일 뿐 집계 원본이 아니다. 질문 대상 TC·관련 증빙부터 읽는다.
2. 원본의 작업 ID+TC ID별 최신 유효 결과 하나만 센다. 재시험·이력·파생 보고서의 같은 ID를 중복 합산하지 않는다. 서로 다른 내용이 같은 ID를 쓰면 충돌을 보고하고 임의 합치지 않는다.
3. 총 개수, 상태별 개수, 각 TC의 내용(조건·행동·기대 결과)·필수 여부·현황·대상 버전·근거/사유를 보고한다. 원본이 일부 없으면 확보 범위와 미확인을 표시하며 전체 개수로 단정하지 않는다. TC 없는 기존 작업은 미정의로 보고하고 임의 사례를 소급 생성하지 않는다.
4. 해당 없음은 개수·사유를 별도 표시한다. 통과율을 제시하면 분모는 전체에서 해당 없음을 뺀 값이며 0이면 산정 불가다. 승인된 취소 항목은 활성 총수에서 제외하고 취소 개수·근거를 별도 표시한다. 미완료를 무단 취소하여 분모에서 빼지 않는다.
5. 버전 변경으로 근거가 무효이면 현재 유효 상태는 미수행(재검증 필요)으로 집계하고 과거 결과를 함께 연결한다. 읽기 전용 조회는 원본을 수정하지 않고 기록 상태와 현재 유효 상태의 차이를 알린다. 근거 유효성을 판단할 자료가 부족하면 미확인과 확인 필요를 표시한다.

일반 답변은 필요한 범위만 대화에 제공한다. **상세 문서 출력을 요청한 때만** `test-cases.ko.md` 같은 ASCII 이름·한국어 본문의 읽기 전용 파생 보고서를 만든다. 원본 경로·버전·작성 시각·범위를 포함하고 같은 범위 보고서는 요청 시 갱신한다. 무관한 기존 파일은 덮어쓰지 않는다. 원본 대신 수정하거나 상시 동기화하지 않는다. 사용자는 index/plan으로 진행을 확인하고 상세 TC는 요청할 때 열 수 있다.

## 증빙과 버전

증빙은 `evidence/T-xx/`에 모든 하위 작업과 함께 고정 보존한다. `<작업ID>-<종류>-<번호>.<확장자>`의 ASCII 이름을 사용하고 과거 판정의 근거를 덮어쓰지 않는다. 로그를 작업/통합 문서에 복제하지 말고 조건·결론과 고정 경로 또는 복구 가능한 버전을 연결한다.

지시에는 기준 입력 버전, 결과에는 실제 입력/출력 버전을 적는다. 커밋·문서 개정·저장 시점·필요한 해시로 식별하며 같은 경로를 같은 내용으로 가정하지 않는다. 통합 판정은 작업 ID·제출 시각·산출물 버전으로 특정한다. 정정·재제출은 이전 이력을 보존하며 미제출 변경과 구분한다.

지시·선행 결과·공통 기준·인터페이스가 바뀌면 영향받은 TC와 수락의 유효성을 평가한다. 영향 평가 전 결과를 후속 작업의 확정 입력으로 쓰지 않는다. 선행 결과·통합 판정의 유효성은 통합 담당자가 판단한다. 유효한 시험은 재사용하고 변경 영향·연결·누락·구체적 위험에만 추가 시험한다. 원본 갱신 담당자는 무효인 현재 TC를 미수행·재검증 필요로 바꾸고 과거 통과 근거는 이력에 유지한다. 과거 수락을 새 버전에 자동 적용하지 않는다.

## 사용자 시험 대기

접근 불가능한 환경은 사용자에게 대상/버전·준비 조건·절차·기대값/실패 기준·회신 자료를 인계한다. 가능한 검증을 마친 뒤 현재 단계를 종료한다. 제출물의 사용자 시험만 남으면 작업은 검토 대기, 항목은 사용자 검증 대기다. 제작 자체가 외부 조건으로 불가능하면 막힘이다.

사용자 검증 대기는 새 환경 설치·보드/원격 제어·별도 시험의 승인이 아니다. 기존 허용 환경은 사용할 수 있지만 추가 실행은 명시적 요청 또는 확정 계획과 유효 총괄 범위가 필요하다. 순차 안내는 [사용자검증](user-validation.md), 결과와 통합 요청을 함께 받으면 통합이 검토한다. 자동 모드에서는 총괄이 배정한다. 응답을 반복 조회하거나 환경을 자동 구축하지 않는다. 회신의 버전·조건·근거가 부족하면 필요한 확인만 요청하며 자체 검증으로 필수 통합 수락을 대신하지 않는다.
