# 작업 식별·상태·결과 기록

개정: 2026-11-17 · 관리 구조 버전: `5`

## 4. 작업 원본

간소 기록도 같은 식별·상태 의미를 쓰되 상태 폴더 생성을 강제하지 않는다. 표준 원본은 `work-items/<status>/<ID>.md` 하나이며 파일명에 제목·날짜·회차를 덧붙이지 않는다. 프로젝트 경계는 기존 index/plan에서 확인하며 초기 구조 생성만 [구조 문서](records-layout.md)를 읽는다.

### 식별과 메타정보

- 상위 ID는 `T-01`, 하위는 `T-01-REV-01`처럼 `T-<상위번호>-<TYPE>-<번호>`다. REV는 결함/완료 조건 수정, EXT는 외부 환경 준비·작업, VAL은 검증 자체가 목적이다. 검증 환경이 외부여도 VAL을 쓰고 단순 사용자 시험 대기로 새 작업을 만들지 않는다.
- 번호는 상위 Task 또는 상위+TYPE별로 순차 부여하고 재사용하지 않는다. 기본 두 자리, 기존 자릿수 유지. 재제출·이동·지시 보완으로 ID를 바꾸지 않는다. 하위 수정도 유형을 중첩하지 않고 같은 상위의 새 REV에 수정 대상을 적는다.
- 새 TYPE은 계획·통합이 대문자 코드·의미·기준을 먼저 정의한다. 여러 Task에 걸친 작업은 책임 상위 하나와 관련 ID로 연결하고 복제하지 않는다. 하위 수락은 상위 자동 완료가 아니다.
- 상단에 ID·요구사항 ID·지시서 개정·담당·갱신 시각·다음 조치/담당·최신 제출 시각/산출물 버전을 적는다. 미제출은 명시한다. 관련된 상위/수정 대상/하위 ID·증빙·대기 사유/해제 조건을 추가한다. 현재 상태는 위치가 원본이며 본문에 중복 상태 필드를 두지 않는다.
- 요구사항·범위·수락 기준 변경은 개정·영향을 기록한다. 담당·위치 갱신은 실질 버전 변경이 아니다. 경로가 없으면 ID로 현재 위치·전환 대응표를 찾고 빈 대체 원본을 만들지 않는다.

### 지시·결과·이력

한 문서에 작업 지시, 최신 수행 결과, TC·검증/미해결 문제, 제출·판정·상태 이력을 짧게 둔다. 결과에는 산출물 역할/경로·결정/영향·실제 입력/출력 버전·미제출 변경·다음 행동을 기록하고 메타정보를 반복하지 않는다. 실제 모델·검증 근거·사용자 시험 요청은 해당 항목에 연결한다.

변경 시 바뀐 항목만 수정하고 관련 참조를 확인한다. 최신 결과만으로 재개 가능하게 유지하되 이전 제출·수락 근거는 보존한다. 이력에는 시각·담당·지시 개정·산출물 버전·판정/이유, 이동 시 전/후 상태를 남긴다. 같은 버전의 재제출도 시각으로 구분한다. 전체 문서·회차별 보고서·별도 압축본을 반복 생성하지 않는다. 상세 로그는 [고정 증빙](records-evidence.md)으로 연결한다. index에는 운영 요약, integration에는 연결 검증·전체 판단만 갱신한다.

### 상태와 권한

| 폴더 | 상태 | 기준 |
|---|---|---|
| 00-planned | 계획됨 | 정의됐으나 시작 조건 미확보 |
| 10-ready | 준비됨 | 입력·접근·선행 조건 확보 |
| 20-in-progress | 진행 중 | 실행 담당자가 실제 수행·자체 검토 중 |
| 30-review-pending | 검토 대기 | 결과/자체 검증 제출 또는 추가 입력·사용자 시험 대기 |
| 40-in-review | 검토 중 | 통합 담당자가 제출 버전 검토 중 |
| 50-changes-requested | 수정 필요 | 완료 조건 미충족·수정 필요 확인 |
| 60-blocked | 막힘 | 외부 조건으로 의미 있는 진행 불가 |
| 90-done | 완료 | 통합 담당자가 수락 |
| 99-cancelled | 취소됨 | 사용자 취소·승인된 범위 변경에 따른 중단/대체 |

준비됨은 실행 허가가 아니다. 계획 작성 완료로 실행 Task를 완료 처리하지 않는다.

- 계획은 Task를 계획됨/준비됨으로 생성하고 제출 상태를 반영하되 수락하지 않는다.
- 실행은 시작 조건을 확인해 준비됨/진행 중, 제출 후 검토 대기로 이동한다. 자기 범위의 수정 필요/막힘을 기록할 수 있지만 검토 중/완료로 옮기지 않는다.
- 통합은 제출 확인 후 검토 중으로 옮겨 완료/수정 필요를 판정한다. 외부 검증·추가 입력 대기 시 검토 대기로 돌리고 다음 행동을 적는다. REV는 계획됨/준비됨으로 생성한다. 수동 수정은 별도 실행 요청, 자동은 유효한 총괄 배정이 필요하다.
- 사용자검증은 인계받은 기존 문서의 항목·근거·이력을 갱신한다. 제출물은 기본 검토 대기이며 시험 통과로 완료 이동하지 않는다. 결함·수정 필요가 확인되면 실패와 수정 필요를 기록할 수 있으나 기존 수락의 변경은 통합에 인계한다. REV 생성은 계획·통합 권한이다.
- 막힘 해제 후 입력·근거를 확인하여 제작 중이면 준비됨, 유효한 제출물의 검토만 남으면 검토 대기로 현재 단계 담당자가 이동한다. 수정 재실행도 실행 요청/유효 배정·조건을 확인하며 연결된 REV와 원래 Task를 중복 실행하지 않는다.
- 완료 후 문제는 통합이 이전 수락 버전·이유를 보존하고 재검토는 검토 대기, 확정 수정은 수정 필요로 돌린다. 다른 역할은 발견 근거를 인계한다.
- 취소는 요청 수신자 또는 자동 총괄이 승인 근거·담당 인계를 확인한 뒤 처리한다. 대체 ID와 요구사항 제외/대체 승인을 연결하며 수락으로 취급하지 않는다.

이동 때 담당·근거·다음 행동과 원본 하나를 확인한다. 중간 중단으로 위치/이력이 다르면 현재 담당자가 마지막 유효 전환·실제 근거로 복구하고 불충분하면 보류한다.

### REV와 현재 현황

원래 Task는 수정 필요에 두고 독립 REV를 연결한다. REV 실행/제출 때 원 Task를 함께 진행 중으로 옮기지 않는다. 통합은 수정 자체와 원 Task의 영향받은 조건을 각각 판정하며 필요한 수정·검증을 모두 충족해야 원 Task를 재수락한다. 연결 수정이 검토에 도달하면 원 Task도 검토할 수 있지만 미해결 사유는 유지한다. 같은 수정은 기존 ID로 재제출하고 별개 요구만 새 REV를 만든다.

index에는 구조 버전·갱신 시각/담당·목표·단계/대상·결정·Task별 ID/제목/기준 상태/담당/링크/다음 행동을 둔다. 실제 상세는 원본에 연결하며 [소유권](common.md)에 따라 배정·제출·판정 등 변화 때 갱신한다. 자동 모드의 운영 항목은 [총괄](orchestration.md)을 따른다. index나 폴더는 프로세스 생존·실시간 검증 근거가 아니다.

중지·보류 요청에는 버전·미제출 변경·유효 증빙·남은 입력·재개 조건을 남기고 멈춘다. 보류를 실패/취소로 바꾸지 않는다. 명시적 재개 후 담당·원본·실제 버전을 확인하고 단순 결과 제출로 재개하지 않는다. 자동 모드의 실행 중단 확인은 총괄 규칙을 따른다.
