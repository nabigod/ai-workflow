# 공통 운영 규칙

개정: 2026-11-08 · 관리 구조 버전: `5`

## 1. 요청 분류와 범위

- 사용자 메시지의 첫머리 또는 명시적 작업 지시 부분에 있는 단계·보조 명령 태그로 요청을 분류한다. 인용문, 코드 블록, 예시, 첨부 문서 속 태그는 명령이 아니다. 워크플로우 검토·개정은 기존 프로젝트 실행·구조 전환 요청이 아니며, 문서 저장만으로 다른 대화에 개정 규칙이 전달됐다고 가정하지 않는다.
- 태그 뒤의 작업 ID, 지시서 경로, 대상 결과물과 자연어 지시로 대상을 정한다. 이동 가능한 경로보다 ID를 우선한다. 예: `[실행] T-03`, `[실행] T-03-REV-01`, `[통합] 보고서 초안 세 개를 통합해 줘`.
- 태그가 없어도 목적이 명확하면 추론한 단계·명령과 범위를 짧게 알리고 진행한다. 분류가 산출물이나 허용 범위를 실질적으로 바꾸면 후보를 최대 두 개 제시해 선택을 받는다. 지원하지 않는 태그나 수동 단계 여러 개의 동시 지시는 한 단계를 선택하도록 요청한다. `[총괄]` 자동 모드는 추론하지 않으며 직접 호출이 필요하다. 이미 명확한 선택은 다시 확인하지 않는다.
- 대상이 하나로 정해지면 진행하고, 여러 작업 중 대상이 불명확할 때만 ID나 범위를 확인한다. 사용자가 지정한 여러 실행 작업은 같은 단계에서 처리할 수 있다.
- 앞 단계 문서가 없어도 현재 단계에 필요한 정보가 있으면 진행한다. 필요한 정보 정리와 짧은 수행 순서는 다른 단계로의 확장이 아니다. 새로운 전체 계획이나 별도 제작 단계가 필요하면 이유와 필요한 다음 지시를 알린다.
- 핵심 요구사항 변경, 큰 범위 확대, 새로운 비용이나 추가 권한이 필요한 결정은 확인한다. 기존 승인 범위 안의 구현·작성 선택과 오류 수정은 진행한다. 준비됨 상태나 수정 지시서 생성 자체는 실행 허가가 아니다. 수동 모드의 다음 단계에는 별도 요청이, 자동 모드에는 [11절](orchestration.md)의 유효한 총괄 배정과 시작 조건 확인이 필요하다.
- 상태 조회는 기록을 읽고 설명하는 요청이며 구조 전환·상태 변경·제작·수락을 시작하지 않는다. `[사용자검증]`은 [13절](user-validation.md), `[커밋]`은 [14절](commit-list.md)의 범위만 수행한다.
- 사용자가 명시적으로 요청한 경우에만 이 워크플로우를 개정한다. 프로젝트 기록과 결과물은 지정된 위치에 저장한다.

공통 기준은 [2절](records.md)의 구조·보관, [담당·소유권](common.md)·[모델·재시도](models.md)의 담당·문서 소유권·모델, [4절](records.md)의 작업 상태·기록, [5절](records.md)의 검증·버전에 둔다. 단계별 절은 이를 참조하며 별도의 상태나 기록 체계를 만들지 않는다.

## 3. 담당과 위임

| 담당 | 책임 |
|---|---|
| 계획 담당 | 요구사항·공통 기준·작업 경계·지시서·배정안, 계획 산출물 확인, 구조 전환 |
| 실행 담당 | 시작 조건 확인, 지정 범위 제작·자체 검증, 제출 |
| 통합 담당 | 결합·전체 검증·실행 결과 수락·수정 지시, 구조 전환, 전체 완료 판정 |
| 사용자검증 담당 | 확정 기준에 따른 사용자 시험 안내·근거 확인·항목 결과 기록 |
| 커밋목록 담당 | 실제 변경 조사·파일 단위 분류·커밋리스트 작성 |
| 총괄 담당 | 명시적 자동 모드의 범위·의존 관계·배정·중지·재개 관리; 수락은 통합 담당에게 위임 |

수동 모드에는 상시 총괄을 두지 않으며 직접 요청 수신자가 질문·위임·종료 보고를 맡는다. 자동 모드에서는 총괄 한 명이 실행·통합을 각각 별도 하위 에이전트에게 맡긴다. 총괄과 통합이 같은 모델이어도 담당자와 책임을 분리한다.

### 위임과 문서 소유권

- 역할별 지정 모델을 준수하며 실행은 실행용 1단계 모델의 별도 담당자 또는 대화에 우선 배정한다. 작업 경계와 인계 비용으로 위임 여부를 판단하되, 직접 수행에도 [모델 배정표](models.md)의 최초 배정 기준을 적용한다. 짧은 작업이나 위임 비용을 이유로 높은 단계의 모델이 실행을 대신하지 않는다. 중요한 결과물은 규모가 작아도 독립 검토를 고려한다.
- 선행 조건을 충족하고 소스·데이터·외부 자원의 수정 소유권이 겹치지 않는 작업만 병렬화한다. 자동 모드는 계획 담당자가 작업지시서에 남긴 병렬 가능 판단을 바탕으로 [11절](orchestration.md)에 따라 총괄이 병렬 배정한다.
- 한 문서의 현재 갱신 담당자는 한 명이다. 착수·재개 전에 위치·담당·최신 기록을 확인하고 제출·검토 착수·수정 반환·단계 종료 때 인계한다. 사용자검증 담당자도 같은 절차로 소유권을 인계받아 해당 단계 동안 유지한다. 이전·이후 담당자가 동시에 수정·이동하지 않으며, 소유권이 불명확하면 해당 쓰기를 보류한다.
- `index.md`는 수동 모드의 계획·통합 담당자가 갱신한다. 수동 사용자검증 담당자는 소유권을 인계받아 검증 현황·다음 조치에 한해 갱신하고 단계 종료 또는 명시적 인계 때 반환한다. 실행 담당자는 생성·갱신하지 않는다.
- 자동 모드의 `index.md`는 총괄이 맡는다. 실행은 자기 작업 문서에, 통합은 검토 대상 작업 문서와 `integration.md`에 결과를 남기며 총괄이 이를 반영한다. 구조 전환 중 계획·통합 담당자에게 `index.md` 갱신이 필요하면 총괄의 쓰기를 멈추고 소유권을 인계한다. 총괄은 통합의 수락 근거를 대신 작성하지 않는다.
- 상태 이동은 [4절](records.md), 사용자검증과 커밋목록의 쓰기 범위는 각각 [13절](user-validation.md)·[14절](commit-list.md)을 따른다. `[커밋]`은 총괄 호출에 포함되지 않는 별도 보조 요청이다.
- 위임 입력은 작업 문서와 필수 참조를 합쳐 [6절](planning.md)을 충족한다. 인계 메시지는 역할·대상 ID, 프로젝트와 현재 작업 문서의 절대 경로, 고정 워크플로우 경로·커밋, 지시서 개정·제출/산출물 버전, 이번 변경점·다음 행동으로 제한한다. 결정·검증·위험의 상세는 원본의 해당 절·증빙으로 연결한다. 인계 메시지를 별도 파일로 중복 보관하지 않는다.
- 환경이 선택을 지원하면 전체 대화 상속 없이 필요한 입력만 전달한다. 생략할 대화의 사용자 결정·제약은 먼저 원본에 반영한다. 새 담당자는 필수 규칙과 원자료를 직접 읽으며, 같은 담당자의 후속 요청은 변경점과 참조만 전달한다. 컨텍스트 유실·압축으로 필요한 내용이 빠지면 관련 원본을 다시 읽는다. 전체 이력 상속이 불가피하면 실제 제한을 알리고 차단했다고 주장하지 않는다.
- 다른 폴더·worktree에서도 원본과 증빙의 접근 경로·상대 경로 기준을 확인한다. 접근할 수 없으면 필요한 본문을 전달하거나 필수 자료 확보 전 관련 작업을 보류한다. 인계 요약으로 범위·수락 기준·사용자 결정·담당/소유권·입출력 버전·미제출 변경·실패 누계·검증 근거·미해결 문제를 잃지 않으며, 실제 결과물과 문서로 재개할 수 있어야 한다.

### Git 기록 제외와 결과물의 사용자 노출

- `.ai-work/`와 운영용 인계 문서는 계속 생성·갱신하되 Git 추적·스테이징·커밋에서 기본 제외한다. 내부 기록에서 제품 커밋·산출물 버전을 참조한다. 저장소의 적절한 제외 설정을 사용하며, 제외에 필요한 `.ai-work/` 경로 표기는 허용한다.
- 이미 추적 중인 관리 파일은 요청 범위 안에서 로컬 자료와 복구 수단을 보존한 뒤 추적에서만 해제한다. 과거 Git 이력을 자동 재작성하지 않는다. [14절](commit-list.md)의 목록 작성처럼 Git 변경 권한이 없는 요청에서는 해제하지 않고 필요한 조치만 알린다.
- Git 제외를 관리 기록 중단·삭제로 해석하지 않는다. 다른 clone·worktree에 관리 기록이 자동 제공된다고 가정하지 말고 접근 경로를 확인한다. 필요한 복구 사본은 Git 추적 여부와 별도로 확보한다.
- 커밋 메시지, 제품 코드·프로젝트 결과물의 주석, PR 설명, 최종 사용자용 문서에는 내부 작업 ID·지시서 파일명·관리 경로를 넣지 않고 변경의 의미를 설명한다. 워크플로우 설명·개정, 내부 관리 문서, 에이전트 인계와 사용자와의 관리 운영 대화에서는 이 식별 정보를 사용할 수 있다.
- 사용자가 대상과 행위를 명시한 경우에만 해당 범위에서 예외를 적용한다. Git 포함 요청을 커밋 메시지나 제품 결과물에 내부 정보를 노출할 허가로 확대하지 않는다.

### 문서 언어와 코드 주석

- 사용자용 관리 Markdown의 제목·본문·판단 근거·검증 결과는 한국어로 작성한다. 코드·식별자·명령어·경로·필요한 원문 인용은 원래 표기를 유지한다. 사용자 지정 언어를 우선하며 무관한 문서를 일괄 번역하지 않는다.
- 새로 작성·수정하는 코드 주석은 영어로 짧게 쓴다. 하드웨어 설계, 규격 제약, 타이밍, 비자명한 설계 이유와 우회 근거처럼 코드만으로 알 수 없는 정보에 한정한다. 필요한 규격 절·항목을 간결하게 연결한다.
- 동작을 풀어 쓰는 주석, 줄마다 붙이는 주석, 교육용 장문 설명은 넣지 않는다. 사용자 설명은 대화로 제공한다. 라이선스, 도구 요구 주석, 안전 조건과 필요한 공개 API 문서는 보존한다. 무관한 기존 주석을 일괄 정리하지 않는다.

### 토큰과 비용 관리

- 환경이 제공하는 사용량만 집계한다. 역할별 입력·캐시 입력·출력과 확인 가능한 추론 사용량, 집계 시각·범위·누락 여부를 한 곳에 기록한다. 출력에 포함된 추론이나 상위·하위 합계를 중복 합산하지 않는다. 수치를 제공하지 않으면 확인 불가로 두며, 이를 알아내기 위한 반복 조회나 별도 수집 환경 구축은 기본 작업에 포함하지 않는다.
- 총괄의 작업 중 표시와 모델 호출을 구분한다. 호출 없는 순수 대기는 토큰 소비로 추정하지 않는다. 총 토큰 수를 비용·앱 사용 한도로 바로 환산하거나 관측 없이 절감률을 제시하지 않는다. 위임은 인계 비용을 추가하므로 총 사용량 절감을 보장하지 않는다.
- 결과 대기는 가능한 완료 이벤트·대기 도구로 처리한다. 토큰을 소비하며 짧은 간격으로 상태를 반복 판단하지 않는다. 자동 알림은 의미 있는 진행·결정·막힘·중지·완료를 중심으로 하되 실행 환경의 필수 진행 안내를 따른다.
- 기록은 [4절](records.md)의 단일 원본·변경 부분 갱신을 따른다. 한국어 Markdown의 짧은 항목과 참조를 사용하며, 토큰 절약만을 위한 별도 AI용 압축본·요약 원장·인코딩본을 유지하지 않는다.
- 경로 전달 뒤 원문을 읽는 입력과 인계 요약을 쓰는 출력도 비용이다. 문서 형식·언어 변경이나 도구의 컨텍스트 압축만으로 절감을 단정하지 않는다. 상태 이동·목록 집계 등 기계적 처리는 검증된 기존 도구가 있으면 활용하되 담당 권한·이력을 유지하며 수락 판단을 대신하지 않는다. 별도 자동화 구축은 필요성과 범위를 정한 작업으로 다룬다.
- 공통 모델 프로필·제약은 기준 문서를 참조하고 작업별 예외와 실제 설정만 기록한다. 다른 문서에 동일한 상세 결과나 `확인 불가`를 복제하지 않는다. 대화의 종료 보고는 결과·제한·다음 행동과 원본 링크를 중심으로 한다.
- 독립적으로 제작·검증·인계할 수 있는 결과물을 작업 단위로 삼는다. 파일·함수마다 쪼개지 않으며, 같은 담당자가 연속 수행할 작은 변경은 묶는다. 제출 전 자체 검증의 범위 내 수정은 원래 작업에서 처리하고 매번 REV를 만들지 않는다.
- 관리량을 줄여도 실제 결과물 검증은 유지한다. 필요하면 소규모 작업의 기록량·인계 횟수·관측 사용량을 비교해 운영을 조정한다.

## 10. 공통 종료 보고

모드·단계·대상, 결과물 위치, 수락 또는 미완료 상태, 수행한 검증과 미검증 항목, 남은 위험·다음 조치를 짧게 보고한다. 표준 방식에서는 현재 작업 문서와 제출 시각·산출물 버전·필요한 증빙을 연결하며 원문 결과를 복제하지 않는다. 모델·사용량은 [담당·소유권](common.md)·[모델·재시도](models.md)의 관측 범위만 보고한다.

수동 모드에서는 필요한 다음 단계와 ID를 명시하고 별도 요청을 기다린다. 자동 모드의 하위 담당자는 총괄에게 인계하며 총괄이 [11절](orchestration.md)에 따라 후속 작업 또는 종료를 판단한다. 구조를 전환했다면 출발·목표 버전, 완료 여부와 남은 항목을 함께 알린다. `[커밋]`은 관리 문서를 새로 만들지 않고 목록 파일·조사 기준·보류 사항으로 보고한다.
